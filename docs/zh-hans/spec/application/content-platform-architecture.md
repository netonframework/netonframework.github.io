# Neton 内容平台套件架构

> 标识：NETON-APP-CONTENT-PLATFORM
> 日期：2026-10-15 · 状态：Draft r3（第二轮评审：定制三分法、媒体关联与授权契约、装配契约基于生成清单、一致性承诺的准确表述、开工顺序；2026-10-15 按首期实现校准：开放分组前缀、事件编解码登记、通用对象事件、媒体 M1、框架已知问题；2026-10-18 增 §5.6 IP 属地端口）
> 范围：内容平台相关开源模块的总体架构、统一契约、对接规则和验收标准。各模块细节见各自规范。

## 1. 定位

**可组合的内容平台基础设施**：一组开源、可独立装配的 Neton Application 模块，加上统一的对接标准。用它搭建资讯、技术资料、汽车与数码评测、UGC 社区、电商内容、短视频、长视频等平台时，**新增一种业务主要是增加业务模块和配置，而不是修改 system、content、comment 等核心模块的代码**。这是本套件的最终验收标准（§12）。

它**不是**「一个 content 模块覆盖所有业务」。内容、评论、互动、采集、搜索、推送是各类平台共享的能力，做成标准模块；商品交易、视频处理、产品参数这些规则差异大的领域，做成独立的领域模块，通过标准对接方式使用共享能力。

**itwind** 是官方样板应用（科技资讯），用来验证架构，并作为开源示例。

## 2. 共享能力与领域模块

### 2.1 共享能力（本套件的标准模块）

| 模块 | 职责 | 规范 |
| --- | --- | --- |
| content | 编辑型内容：类型、分类法、合集、版本、审核、发布、撤回、查询 | [content-module.md](content-module.md) |
| comment | 评论：盖楼 / 楼中楼、支持反对、热评、治理、导入 | [comment-module.md](comment-module.md) |
| interaction | 互动：收藏、点赞、关注、足迹（各自语义，§2.3） | [interaction-module.md](interaction-module.md) |
| collect | 内容接入流程：采集、清洗映射、去重、策略检查、投递 | [collect-module.md](collect-module.md) |
| filter | 筛选器：模块注册数据源与维度，存下来的查询跨模块复用；频道、楼层、合集规则、推送订阅都引用它 | [filter-module.md](filter-module.md) |
| search | 跨模块统一搜索（相关性；与 filter 共享维度索引，见 filter §12.3） | 待写 |
| push | 推送：设备、主题、下发、多通道 | [push-module.md](push-module.md) |
| 媒体（infra） | 文件与视频的上传、存储、处理、访问控制 | §6 |

### 2.2 领域模块（独立建设，不并入 content）

| 领域 | 自己负责的东西 | 与共享能力的关系 |
| --- | --- | --- |
| 实体库（catalog） | 实体（品牌 / 车系 / 车型、手机型号……）、参数定义、配置版本、对比 | 实体可被评论、收藏、评价；文章可关联实体 |
| 口碑（review） | 多维评分、评价、聚合分与分布 | 评价可被评论、点赞 |
| 电商（commerce） | 商品、SKU、价格、库存、订单、支付、退款 | 商品详情可关联文章和视频；商品可被评论、收藏；**商品本身由商品模块负责** |
| 视频（video） | 播放授权、清晰度、字幕、分发、播放统计 | 视频文件的上传和转码走媒体标准（§6）；视频作为内容展示时是 content 的一个类型，引用视频资产 |
| 社区（community） | 圈子、帖子、问答 | 帖子可被评论、点赞；与编辑型内容的审核发布流程不同，不复用 content 的生命周期 |

### 2.3 拆分原则

一个能力单独成模块，要同时满足三条：
1. 至少两类平台需要。
2. 能作用于多种对象，不绑定某一种业务实体。
3. 有自己的数据和生命周期。

同一模块里的不同能力**不强行共享生命周期和存储规则**。例如 interaction 里：
- 收藏：持久，可分组。
- 点赞：计数为主，可撤销。
- 关注：带通知订阅。
- 足迹：有保留期、可清空。

它们共享对象引用和授权接入方式，但各有各的表和规则。

## 3. 分层与依赖

```
┌──────────────────────────────────────────────────────────────────┐
│ 产品层      itwind · 你的应用：品牌、类型注册、配置、产品特有模块        │
├──────────────────────────────────────────────────────────────────┤
│ 领域模块    catalog · review · commerce · video · community …       │
├──────────────────────────────────────────────────────────────────┤
│ 共享能力    content · comment · interaction · collect · search · push│
├──────────────────────────────────────────────────────────────────┤
│ 基础模块    system · infra（含媒体）· account · member · platform    │
├──────────────────────────────────────────────────────────────────┤
│ 契约库      neton-application-contract                             │
├──────────────────────────────────────────────────────────────────┤
│ Neton 框架  core · http · routing · database · redis · jobs · ai    │
└──────────────────────────────────────────────────────────────────┘
```

- 只依赖下层或同层模块的 **contract 子工程**，从不依赖其他模块的实现。
- **依赖 contract 也是耦合**：每个模块在装配清单（§8）里显式声明依赖哪些模块的哪个契约版本。模块之间的依赖图必须无环，CI 检查。
- 基础模块不知道上层模块的存在；框架不知道 Application 的存在。
- 部署模型是**单租户**：一套部署就是一个平台，模块里不设租户字段，不做租户隔离。

## 4. 对接标准

### 4.1 总规则

**所有模块之间、模块与产品之间的对接，都必须走被对接方规范里定义的标准方式。** 标准方式只有以下几种：

| 方式 | 用途 | 例子 |
| --- | --- | --- |
| 契约接口（端口） | 同步调用另一个模块的能力 | `ContentDraftWriter`、`CommentImporter`、`MediaService` |
| 注册表 | 向另一个模块声明自己的类型、策略、解析器 | 内容类型、上传业务类型、对象解析器、投递端口 |
| 事件 | 通知别的模块某件事发生了 | `content.item.published` |
| 配置定义 | 产品调整模块行为 | 类型化配置项 |
| HTTP 接口 | 客户端、外部系统接入 | `/app/*`、`/admin/*`、`/platform/*` |

禁止的做法：
- 读写别的模块的表。
- 调用别的模块的非契约类。
- 用裸 URL 代替**平台托管媒体**的资源身份（平台托管的文件必须用 MediaRef，§6）。合法的外部链接、来源原文链接可以存在，但必须用明确的类型（`ExternalLink`）保存，并经过链接安全策略（协议白名单、展示时的跳转提示等）。
- 在产品代码里复制一份别的模块的逻辑。
- 为某个产品在通用模块里加 `if` 分支。

### 4.2 定制的三种情况

| 情况 | 判断 | 做法 |
| --- | --- | --- |
| **已有扩展点能表达** | 能用注册类型、配置、实现端口 / 策略、订阅事件做到 | 产品提供策略、适配器或类型注册，**不改基础模块** |
| **缺少通用扩展机制** | 这类定制至少两类产品都会遇到（套用 §2.3 的拆分原则），但现有扩展点表达不了 | 在被对接模块的规范里补一个通用扩展点（端口、注册项、配置项或事件），评审后进入标准，再按新标准对接 |
| **纯产品特殊规则** | 只有这个产品需要 | 留在产品模块里，通过已有扩展点挂接；**不升级为公共标准** |

- 不允许绕过标准做私有对接（读别人的表、调用非契约类）。三种情况里都只是「怎么接」不同，接法本身始终是标准的。
- 规范里每个扩展点都写清楚：谁实现、谁调用、什么时候调用、失败怎么处理。

### 4.3 标准不是死板

标准化约束的是**对接方式**，不约束**业务表达**：
- 产品可以注册任意内容类型、字段、分类法、上传业务类型。
- 产品可以选择评论展示形态、热度公式、审核模式、采集规则。
- 产品可以写自己的领域模块。

只有「怎么接」是统一的。

## 5. 统一契约（neton-application-contract）

契约库只放**稳定的跨模块基础类型**，越少越好；各模块自己的端口、DTO、事件放在各自的 `contract` 子工程里。

### 5.1 对象引用

```kotlin
data class ObjectRef(val type: String, val id: String)    // ObjectRef("content.item", "1024")
```

类型命名 `<模块>.<实体>`。所有作用于任意对象的能力（评论、互动、评价、搜索、推送深链）都用它指代目标。

### 5.2 对象解析与授权分离

两个问题分开回答：

| 问题 | 接口 | 说明 |
| --- | --- | --- |
| **这种对象支持什么能力** | `ObjectResolver.describe(refs)` → `ObjectSummary` | 存在性、标题、摘要、封面、链接、拥有者，以及 `capabilities`（如 `comment`、`favorite`、`review`）。这是对象**类型和状态**层面的事实：单页不支持评论，未发布的内容不支持收藏 |
| **在卡片流里怎么显示** | `ObjectResolver.views(ids, viewer)` → 每个对象一份 JSON（可选，默认不提供） | 与拥有模块**原生列表接口里的一项同形**（content 的文章卡片、comment 的评论条目）。只给访问者此刻可见的对象。筛选器的卡片流（频道、楼层、`/app/filter/{id}`）把它附在 `Card.view` 上，客户端沿用已有模型渲染；没有视图的类型退回 `ObjectSummary` |
| **这个人现在能不能对它做这件事** | `ObjectAccessPolicy.check(viewer, ref, action)` → 允许 / 拒绝(原因) | 由**拥有对象的模块**实现，考虑可见性（会员可见、密码访问）、对象自身设置（关闭评论）、用户状态（被禁言另由评论模块判断）等 |

- 使用方（如 comment）在用户操作前必须调用 `check`，`capabilities` 只用于界面展示和快速过滤，**不能代替授权检查**。
- 解析结果只包含对外可展示的信息；拥有者模块不能通过解析器暴露越权数据，使用方也不能拿解析结果绕过拥有者的权限检查。
- 所有接口都是批量的，避免逐条查询。

### 5.3 事件与投递保证

基于框架的 `DomainEventBus`（同步监听者；声明为可重试的监听者经 `DomainEventStore` 落库后异步投递）。每个事件在发布方规范里写明投递方式：

| 方式 | 保证 | 适用 |
| --- | --- | --- |
| 同步（事务内） | 监听者在发布方的数据库事务里执行，写入一起提交或一起回滚。**只允许写本库数据**，不允许在事务里调用外部系统 | 必须和主数据一致的派生数据，如评论数回写 |
| 可重试（事务性 outbox） | **业务变更和待投递的事件记录在同一个数据库事务里提交**；提交后由投递器读取事件记录，调用监听者或外部系统。至少一次，失败按退避重试，超过次数进入死信并告警，可人工重投 | 推送、搜索索引、外部通知、采集回写 |

约定：
- 不承诺「恰好一次」：消费方必须按事件 ID 幂等，并能在投递器重启、重复投递后恢复到正确状态。
- 不承诺全局顺序：同一对象的事件带单调递增的 `subjectVersion`，消费方据此丢弃过期事件。
- 不允许在事务提交前直接向外部系统发送任何东西；外部副作用一律走可重试投递。
- 事件信封：`id`、`type`（`<模块>.<实体>.<过去式动作>`）、`version`（载荷版本）、`subject`（ObjectRef）、`subjectVersion`、`actor`、`occurredAt`、`data`（只放 ID 和少量摘要）。实现上是契约库的 `contract.core.SuiteEvent : DomainEvent` 接口（`eventId`、`type`、`subject`、`subjectVersion`、`actor`、`occurredAt`），载荷字段直接是事件类的属性；`eventId` 用 `EventIds.next(now)` 生成。
- **通用对象事件**（契约库 `contract.core`，任何拥有对象的模块都可发布、任何能力模块都可订阅，双方互不认识）：`ObjectViewed`（`object.viewed`，详情读取时发布，足迹 / 热度用）、`ObjectUnavailable`（`object.unavailable`，`permanent` 区分暂时下线与彻底删除）、`ObjectAvailable`（`object.available`）、`ObjectCounterChanged`（`object.counter_changed`，counter = `comments` / `favorites` / `likes` / `follows`，value 为绝对值，由计数维护方在同一事务内发布、对象拥有方同步回写）。模块不再各自定义「已浏览」「计数变化」之类的同义事件。
- 发布在 `db.transaction { … bus.publish(event) }` 内进行；监听者实现 `DomainEventListener<E>`，`listenerId` 形如 `<模块>.<用途>`，稳定不变（写进投递记录），按上表选 `DeliveryMode.SYNC` 或 `RETRYABLE`。
- **事件编解码登记**：可重试投递要把事件序列化进 `DomainEventStore`。infra 在 bootstrap 里绑定默认的 `SerializerDomainEventCodec`；**发布方和订阅方**都在自己的 bootstrap 里登记用到的事件类型：`(ctx.getOrNull(DomainEventCodec::class) as? SerializerDomainEventCodec)?.register(X::class, X.serializer())`（重复登记同一 serializer 无害）。未登记的类型无法走可重试投递。
- 每个模块在规范里列出自己发布的事件、投递方式和载荷；这些都是公开契约，变更遵循 §10 的版本规则。

### 5.4 模块实现约定

| 方面 | 约定 |
| --- | --- |
| 仓库 | 每个模块一个服务端仓库 `neton-application-module-<name>`（根工程是实现，`contract/` 子工程是公开契约，宿主以 `:module-<name>-contract` 装配）和一个后台页面仓库 `neton-application-front-<name>` |
| 依赖 | 只依赖基础模块（system、infra）的实现，以及其他套件模块的 contract 子工程 |
| 数据 | 只支持 PostgreSQL；表名以模块名为前缀；只经 migrate 建表和升级；不读别的模块的表。结构化字段以 `text` 列存 JSON（框架行映射只支持 Long / Int / Double / Float / Boolean / ByteArray / String，不支持 jsonb），数组同理；需要在 SQL 里取值时临时 `::jsonb`，需要按字段筛选的走各模块的索引表 |
| 接口分组 | `/app/<模块>/*`（终端用户，账号令牌）、`/admin/<模块>/*`（后台，管理员令牌）、`/platform/<模块>/*`（外部系统，签名鉴权）。分组由 controller 所在包决定（`controller.app.*` / `controller.admin.*` / `controller.open.*`），`@Controller` 只写业务前缀；**开放分组的包名是 `open`，但挂载前缀是 `/platform`，没有 `/open/*` 路径**。套件模块不依赖 platform 模块的实现，开放接口的签名由模块自带（如 collect 的 `collect_workers` + HMAC-SHA256） |
| 分页 | 终端用户列表用游标分页（`cursor` + `limit`，响应 `{ list, nextCursor }`）；后台表格用页码分页（`pageNo` + `pageSize`） |
| 写接口 | 幂等语义写进规范（重复收藏、重复投递不产生重复数据）；按用户限流 |
| 错误 | 消息只写大写下划线机器码，前端按码翻译；访问拒绝统一经契约库的 `AccessDecision.orThrow()` 映射（不存在 404、需登录 401、其余 403） |
| 校验 | 入参在业务逻辑里显式校验，不只依赖 DTO 注解 |
| 权限 | `<模块>:<资源>:<动作>`，资源段与后台路由段一致（`/admin/push/topic/page` → `push:topic:query`；带连字符的资源照写，如 `comment:sensitive-word:query`）；动作用 `query` / `create` / `update` / `delete` 及少量业务动作（`send`、`run`、`review`、`retry`……）；只声明，角色由 system 管理；全部出现在后台菜单种子里（页面 type=2 用 query，其余为按钮 type=3），默认授予 `super_admin` |
| 配置 | system 的类型化配置定义（`SettingDefinition`） |
| 测试 | 单元测试 + 宿主装配后的真库验证 + 契约测试 |
| 装配 | 依赖 `ObjectRegistry` 的逻辑类在 `init/<Name>RuntimeBootstrap` 里手工构造并 `ctx.bind`（不用 @Logic，它早于 bootstrap）；共享注册表一律 `bindIfAbsent`，与装配先后无关 |

### 5.5 框架已知问题（2026-10-15）

- **numeric 列让原生数据库驱动崩溃（已修复）**：sqlx4k 1.15 及以前，带参数查询结果里的 PostgreSQL `numeric` 列（`SUM`、`AVG` 等聚合的默认返回类型）会让原生驱动崩溃整个进程。修复由我们提交上游（sqlx4k #184），随 1.16.0 发布，框架已升级（2026-10-17）。现在 `numeric` 按文本精确返回；聚合要当整数用时照常写 `::bigint`，那是取值类型的选择，不再是规避。
- **出站 HTTP/2 带 Host 头**：hyper4k 客户端在 HTTP/2 请求里仍带 `Host` 与连接类头部，严格的 h2 服务端（如开了 h2 的 nginx）直接返回 400。已在 hyper4k `d436919` 修复（h2 下去掉这些头，HTTP/1.1 不变），但尚未发布版本。影响所有出站请求：collect 抓取、infra `importFromUrl`、push 的 FCM 调用等；发版前遇到这类 400 先按此排查。

### 5.6 IP 属地

评论、帖子、后台的注册 / 登录记录都要显示「IP 属地」。解析能力只实现一次，经契约库的端口共享，使用方不依赖地理库，也不依赖彼此：

```kotlin
// contract.core
fun interface IpRegionResolver { suspend fun region(ip: String): IpRegion? }
data class IpRegion(countryCode?, country?, province?, city?, display)   // IpRegion.UNKNOWN = display「未知」
object IpRegions { fun display(countryCode, country, province); fun classify(ip): PUBLIC / NON_PUBLIC / INVALID }
```

| 方面 | 约定 |
| --- | --- |
| 实现方 | infra 的 `logic.GeoLiteIpRegionResolver`（本地 GeoLite2 City 库，进程内查询，不出网），在 bootstrap 里 `bindIfAbsent`；宿主先绑定自己的实现即可替换（商业库、在线服务）。库路径是宿主 `config/geolite.conf` 的 `path`（缺省 `./data/geoip/GeoLite2-City.mmdb`），首次查询时读入内存，不用属地的宿主不付这份内存 |
| 使用方 | 请求时 `ctx.getOrNull(IpRegionResolver::class)`，拿不到就不记录；目前是 account（后台的注册 / 登录属地）与 comment（评论的 IP 属地，见 comment 规范 §3.2） |
| 地址来源 | 只用框架解析后的可信客户端地址 `HttpRequest.clientAddress`（对端不是 `ratelimit.trusted_proxies` 时就是 TCP 对端，是可信代理时才从右往左剥 `X-Forwarded-For`），与限流、网络准入同一个值；客户端传不进来 |
| 展示规则 | `IpRegion.display`，所有实现共用 `IpRegions.display`：中国大陆显示省级（去掉「省」「市」「自治区」等后缀，「广东」「广西」「北京」，没有省级信息时「中国」）；香港、澳门、台湾显示「中国香港」「中国澳门」「中国台湾」；其他国家和地区显示国家名（「美国」）；私有、回环、链路本地、CGNAT、文档、组播等地址和库里查不到的公网地址显示「未知」 |
| 给不出结论 | 返回 null：库未配置或损坏、地址不合法。使用方此时**不保存任何属地**，而不是把「未知」写进数据 |
| 失败 | 实现不抛异常、只做本地或带短超时的缓存查询；使用方在写请求路径上同步调用 |
| 存储 | 使用方只存展示文本（comment 的 `ip_region`），不存原始 IP |

## 6. 媒体标准（infra）

产品图、新闻配图、评论图片、用户头像、视频，**凡是平台托管的文件，一律经 infra 上传、存储和访问**，业务模块只保存媒体引用。分工：

> **infra 负责文件与派生资源；业务模块决定对象能否被访问；二者通过授权契约协作。**

完整规范见 [infra-media.md](infra-media.md)，这里列出各模块必须遵守的部分。

### 6.1 媒体引用

```kotlin
data class MediaRef(val fileId: String)
```

- 业务数据存 MediaRef，不存平台托管文件的 URL；展示地址由 infra 按访问者和存储配置生成。
- 接口响应把 MediaRef 批量展开成 `{ fileId, url, width?, height?, duration?, mimeType, variants?, status }`。M1 实际是 `port.MediaView(fileId, url, mimeType, size, businessType, lifecycle, expiresAt?)`，宽高、时长、派生版本随 M2 / M4。

### 6.2 关联契约：上传成功不等于可以使用

文件上传后处于**临时**状态，必须经业务模块**确认关联**才进入生命周期：

```kotlin
// port.MediaService（M1）：owner 用 ObjectRef 的 type / id 字符串；actorUserId 为应用账号，后台 / 系统操作传 null
mediaService.attach(fileId, ownerType = "content.item", ownerId = "1024", usage = "content.image", actorUserId)   // → Attached / Rejected(MediaErrorCode)
mediaService.detach(fileId, "content.item", "1024", "content.image")
mediaService.detachAll("content.item", "1024")
```

`attach` 时 infra 校验：
1. 文件存在且未被清理。
2. 文件的上传业务类型与 `usage` 匹配（评论图不能挂到商品图集）。
3. 处理状态允许关联（视频未处理完成时，只有声明接受处理中状态的用途可以关联）。
4. 操作者有权使用该文件：临时文件只能由上传者本人关联；已关联的公开文件被再次引用时，需要用途声明允许复用。

此外：
- 同一文件可以被多个对象引用，每个引用单独登记；删除一个对象只解除它自己的引用，不影响其他对象。
- 临时文件超过宽限期仍未关联就清理。清理与关联并发时由 infra 保证互斥：已开始关联的文件不会被清理，已进入清理的文件拒绝关联。

### 6.3 访问策略

| 场景 | 策略 |
| --- | --- |
| 公开内容的图片、头像 | 公开读取，可用长期 CDN 地址 |
| 草稿、待审内容的附件 | 只有有权查看该草稿的人可读，只发短期签名地址 |
| 私密评论图片、会员可见内容的媒体 | 由拥有模块的访问策略按引用对象的状态判断，只发短期签名地址 |

- 访问策略按**引用**判断：一个文件同时被公开对象和私密对象引用时，只要访问者能看到任一引用对象就可以访问。
- 非公开资源**不生成永久公开地址**；签名地址有有效期，引用对象变为不可见后，新的访问请求不再签发地址。

### 6.4 外部链接

来源原文链接、合作方跳转、正文里的外链用 `ExternalLink(url, kind, rel)` 保存，不当作平台媒体：
- 协议白名单（http / https）。
- 展示时按策略加跳转提示，或标注 nofollow。
- 不经平台代理下载、不进媒体生命周期。

需要把外部文件纳入平台的（例如采集到的图片），经 infra 的服务端转存变成 MediaRef。

### 6.5 现状与补齐

| 能力 | 现状（2026-10-15） | 首个闭环是否需要 |
| --- | --- | --- |
| 单文件上传 + businessType 策略 + 内容寻址 + 公开 / 本人可见 | 已有 | — |
| 模块注册 businessType | M1 已实现（`FileBusinessPolicyRegistry`） | 需要 |
| 临时文件 → 关联确认（attach / detach）与校验 | M1 已实现 | 需要 |
| 按引用的委托访问策略、短期签名地址 | M1 已实现（唯一绑定的 `port.MediaOwnerAccess`，套件模块 `bindIfAbsent` 同一段代码，经 `ObjectRegistry` 按类型路由） | 需要 |
| 无引用文件的安全清理（宽限期 + 并发保护） | M1 已实现（`infra-media-cleanup`） | 需要 |
| 服务端转存外部文件 | M1 已实现（DNS / 重定向型 SSRF 未覆盖，见 infra-media §11） | 需要（采集） |
| 后台媒体上传与读取 | 已实现（`/admin/infra/media/upload`、`/admin/infra/media/get/{fileId}`） | 需要（后台编辑器） |
| 图片派生版本 | 只有策略字段 | 按首个产品的需要决定（列表缩略图可先由客户端按原图处理） |
| 分片 / 断点续传 | 没有 | 不需要；视频或大文件场景启动时排期 |
| 视频处理（转码、截帧、时长） | 没有（PrivChat 服务端有实现，不在 infra） | 不需要；**视频场景立项时同步排期**，不因编号靠后而无限后置 |

## 7. 标准化的核心语义

接口命名和目录结构一致还不够，以下语义在各模块规范里必须**写死**，这是模块可复用的前提：

### 7.1 content

- **身份与版本分离**：内容 ID 稳定，正文属于版本。「当前草稿」和「线上版本」同时存在，编辑不影响线上，直到新版本审核通过。
- **状态转换**：草稿、待审、定时、已发布、已撤回、已归档、回收站。每个转换有明确的触发者和权限点，不合法的转换直接拒绝。
- **类型扩展**：类型特有字段放在类型定义的字段集里，不往内容主表加可空列。
- **删除与引用**：撤回、删除后，评论、收藏、搜索、推送深链、合集条目的行为明确（见 content 规范的「生命周期影响」一节）。
- **一致性**：状态写入和待投递的事件记录在同一事务内提交（事务性 outbox，§5.3）。

### 7.2 comment

- **目标与上下文**：目标是 ObjectRef；楼层、根评论、父评论的关系和楼号分配规则。
- **可见性矩阵**：待审、公开、折叠、隐藏、删除对作者本人、其他用户、对象拥有者、管理员分别可见什么。
- **删除保留结构**：作者删除和管理员删除都保留占位，楼层和引用链不塌，占位文案不同。
- **计数定义**：评论数、回复数、参与人数各自包含哪些状态（见 comment 规范的「计数定义」一节）。
- **一致性**：楼号原子分配；游标分页有明确的排序键、游标格式和快照边界（见 comment 规范「一致性」一节），只对「遍历期间一直存在且一直可见」的评论承诺不重复、不遗漏。

### 7.3 collect

采集是**内容接入流程**，不是直接写表：

> 采集 → 原始记录 → 清洗与映射 → 去重 → 策略检查 → 调用目标模块的契约接口入库

- 采集的结果默认进入**草稿或审核**，抓取成功不等于允许发布；免审只能由目标模块的发布策略显式放行。
- 记录带**来源信息**：来源、原始地址、采集时间、合作关系与使用范围、采集器与规则版本，可追溯到每次运行。
- 支持断点恢复、失败重试、来源更新同步，并定义「上游删除或下架时，已入库内容怎么处理」的策略（见 collect 规范）。

## 8. 装配契约（模块清单）

装配契约**不另造一套手写清单**，而是扩展框架现有的生成机制：

- 框架已经由 KSP 从 `@NetonModule` 生成模块清单（ModuleManifest），聚合模块的 logic、路由、定时任务、校验器和迁移；应用通过 KSP 参数 `neton.modules` 决定装配哪些模块。
- 装配契约在这份生成清单上扩展，**单一事实来源规则**如下：

| 信息 | 事实来源 | 进入清单的方式 |
| --- | --- | --- |
| 模块依赖 | Gradle 依赖声明（只依赖其他模块的 `contract` 子工程） | 构建时读取 |
| 提供的端口、对象解析器、访问策略、投递端口、注册表 | 代码中的注解或注册调用 | KSP 生成 |
| 路由（含分组）、权限点、定时任务、迁移 | 代码（现有机制） | KSP 生成 |
| 配置定义 | 类型化配置定义 | KSP 生成 |
| 发布 / 订阅的事件及投递方式 | 事件类型声明和监听者注解 | KSP 生成 |
| 可选依赖缺失时的降级行为 | 代码中的可选依赖声明（带降级说明） | KSP 生成 |
| 模块描述、分类、文档链接、截图 | 人工维护的少量元数据文件 | 合并进清单，**只能写描述性字段**，不能声明依赖、接口或权限 |

- 冲突时以代码和 Gradle 为准；人工元数据出现非描述性字段时构建失败。
- 生成的清单是构建产物，不入库；CI 检查：
  - 依赖图无环。
  - 契约版本兼容。
  - 声明的端口都有实现。
  - 权限点在后台菜单中有归属。
- 管理端页面随模块提供（后台通用）；面向用户的展示因平台而异，不强求统一页面，套件只提供客户端 SDK 和可选的基础组件（评论区、评分卡片、富文本块渲染器）。

## 9. 工具链与 MCP

装配和检查做成**可测试的库和命令行工具**（`neton` CLI），MCP 只是它的适配层：

| 层 | 内容 |
| --- | --- |
| 核心库 | 读取模块清单、解析依赖、检查版本兼容和依赖环、生成装配配置、生成类型注册代码、运行契约测试 |
| CLI | `neton module list/add/remove`、`neton dist create/check`、`neton scaffold type/module` |
| Builder MCP | 把 CLI 能力暴露给 AI 编程助手；不包含任何 CLI 之外的构建逻辑 |
| 运行期模块 MCP | 把已运行应用的模块能力（查询内容、创建草稿、审核评论、运行采集任务）暴露为工具。鉴权经 platform 应用，工具映射到权限点；写操作默认只产生草稿或待审结果；全部审计 |

框架目前只有 MCP 客户端（neton-ai），MCP 服务端协议需要在框架中实现。

## 10. 版本与开源

- 每个模块独立 semver；`contract` 子工程和公开事件的不兼容变更决定主版本号。1.0 之前允许不兼容变更，但 CHANGELOG 必须写明迁移方式。
- 套件发布时提供「框架版本 × 模块版本」兼容表。
- 每个模块一对仓库（服务端 + 后台页面），规范统一维护在 neton-docs。
- CI：构建、单测、真库测试、契约测试、依赖环检查、前端类型检查、依赖审计。
- 许可证：待定（套件与样板应用统一选型）。

## 12. 验收标准

### 12.1 第一个端到端闭环（路线步骤 4）

> 采集文章 → 生成草稿 → 审核发布 → 用户评论 → 收藏 → 产生搜索索引与推送事件 → 撤回 → 评论、收藏、搜索、推送深链的可见性随之正确变化

全部用真实数据库、真实模块装配的自动化测试覆盖，不用替身绕过模块边界。

### 12.2 通用性验证（路线步骤 5）

用一个非文章对象（最小实体）接入评论和收藏。通过标准：content、comment、interaction 的代码零改动，只新增实体模块、它的对象解析器和访问策略、配置。

### 12.3 总标准

**新增一种内容业务时，主要工作是增加业务模块和配置，而不是修改核心模块代码。** 如果某次新增业务需要改核心模块，按 §4.2 把对应对接点标准化，再计入模块规范。
