## 2. 证据与现状边界

- 本地框架 `ClientIpResolver` 从传输层 `peerAddress` 出发；仅当对端属于 `ratelimit.trusted_proxies` 时解析转发头。未配置时使用对端 IP。
- 解析 `X-Forwarded-For` 时从右到左剥离可信代理；没有可用的不可信节点时，当前实现会回退到 `X-Real-IP`，最后回退对端。
- 路由限流在 handler 执行前发生，统计请求，不区分登录成功或失败。它不能代替应用层失败计数。
- 评审会话报告：线上未配置框架可信代理；Next.js 服务端代理未转发客户端 IP，导致相关路由按本机代理 IP 共享额度。这是外部评审提供的线上证据，本文编写过程未独立登录服务器复验。
- 评审会话在独立 Caddy v2.10.2 实例中的实验显示：该实验配置覆盖外部 `X-Forwarded-For`，但透传 `X-Real-IP`。这不是对任意 Caddy 配置、版本或 CDN 拓扑的保证。

“共享额度”指同一受限路由/动作下的来源合并，不表示登录、注册、发短信共用同一个全局计数键。最终以实际 key 与部署结果为准。

建立类似权限字符串检查的静态契约 gate：从生成路由元数据枚举全部匿名认证入口，以及发送/消费验证码的入口，断言存在有效限流策略和清单条目。允许继承的组级策略；检查有效策略而不只 grep 方法注解。新增入口、路由别名、fork 路由遗漏或失效策略使 gate 失败。静态 gate 之外仍须验证 429 的运行时行为。

## 3. P0-a：可信代理链契约

### 3.1 支持的部署拓扑

本阶段支持以下同机部署：

```text
客户端 → Caddy → Neton 后端
客户端 → Caddy → Next.js 服务端代理 → Neton 后端
```

Neton 和 Next.js 仅通过受控入口访问。8800、3001、3002 是当前评审中的端口示例，实施时必须核对实际监听地址、容器映射及防火墙规则，包括 IPv4/IPv6。

若增加 CDN、负载均衡、容器网桥或远程代理，必须重新列出每一跳及信任边界；不得直接套用本机配置。

### 3.2 配置与转发规则

框架实际加载的 `config/routing.conf`（或对应环境覆盖文件）配置：

```toml
[ratelimit]
trusted_proxies = "127.0.0.1,::1"
```

当前该配置与网关 `NEWGATE_TRUSTED_PROXIES` 独立；目标是全应用只保留一份生效的可信代理策略。本阶段以现有 `routing.conf` 字段作为兼容入口，由框架请求层统一使用。实施必须验证当前发布包支持并实际加载此配置。信任列表须匹配实际传输对端的规范化地址；禁止为了通过验收而信任任意来源。

在相关 Caddy `reverse_proxy` 块中清理外部头：

```caddyfile
reverse_proxy 127.0.0.1:8800 {
    header_up -X-Real-IP
}
```

上例只展示后端上游；代理到 Next.js 的入口同样须清理 `X-Real-IP`。配置必须位于实际命中的反向代理块内，并检查其他规则是否重新注入该头。

Next.js 服务端代理必须：

1. 仅在只能由可信入口到达的部署前提下，保留经验证的 `X-Forwarded-For` 链；必须实测部署版本的 `next start`、中间件和服务端代理是否追加/改写转发头，不能只检查 fetch 代码就认定原样传递。不取最左项、不把未经验证的浏览器头当真实 IP。
2. 不再转发 `X-Real-IP`；仅转发所需请求头，不通过整体复制请求头引入旁路。
3. 覆盖登录、注册、短信和找回密码等全部代理路径，避免单独修复登录路径。
4. 缺少可信来源头时不编造 IP，记录可观测事件；后端仍按传输对端限流。持续缺头应作为部署异常处理，不能宣称来源隔离已成立。

信任回环地址意味着信任本机进程。本机不可信进程、SSRF 和可直达 Next.js 的旁路不在“外部浏览器无法伪造 IP”的结论内，应通过部署隔离与入口控制约束。

### 3.3 框架统一来源契约与迁移

P0-a 包含框架请求来源契约修改，不再视为纯部署配置变更；不修改认证/授权抽象。实现前须在框架 HTTP/routing 契约中确定共享字段或请求上下文访问器、初始化位置和各适配器一致性。

- 每个入站请求在安全决策与审计执行前，从不可伪造的 `peerAddress` 和一份不可变配置快照解析一次来源，保存为只读请求值。限流、网关 Key IP 白名单、会员登录/注册审计均消费该值，不再各自解析头。
- `peerAddress` 保留原始传输对端语义。现有可能直接取 XFF 最左项的 `remoteAddress` 不能直接作为安全来源；迁移须区分传输对端与可信客户端 IP，不默默改变旧字段语义。
- 默认不读取 `X-Real-IP`；XFF 缺失或全为可信节点时回退传输对端。畸形/重复头策略必须统一并测试，不能让无效 IP 成为白名单或限流键。缺失有效对端时应显式表示 unknown，白名单拒绝，限流进入受控兜底桶。
- 如确需 X-Real-IP，必须由共享策略显式开启，且只对可信对端生效；配置字段命名在框架契约评审时冻结，默认关闭。即使部署遗漏 Caddy 清理，默认行为也不得采信该头。
- 移除会员控制器“只取 TCP 对端”的私有 helper，并更新其旧部署假设注释；移除网关独立解析路径。`NEWGATE_TRUSTED_PROXIES` 迁移期只能作为兼容输入：仅旧配置存在时统一映射并告警，两份配置规范化后冲突则启动失败，禁止两套策略同时生效。
- 配置加载、请求初始化不能只发生在带 `@RateLimit` 的路由上。发布框架包并升级全部消费者后，才算迁移完成；新请求使用新策略快照，同一请求不受中途配置变更影响。

### 3.4 发布与回退

发布前保存相关配置与前端版本，检查配置语法，先在隔离环境用实际站点配置复现链路，再验证后端最终解析出的 IP 和限流桶。发布顺序应避免出现“已信任代理但未清理不可信头”的窗口；优先完成入口清理及 Next.js 转发，再启用后端信任配置。

上线后检查正常登录、来源分桶及 429 分布。回退须将配置和代理版本作为一组评估；不得以关闭限流作为回退方案。回退到共享代理 IP 会恢复原可用性风险，必要时临时收紧管理入口并继续修复。

## 4. P0-b：登录防护设计约束

### 4.1 分层计数

| 维度 | 统计内容 | 行为 |
| --- | --- | --- |
| 路由/动作 + IP | 所有请求，包括成功请求 | 在密码哈希计算前限制频率 |
| 认证域 + 账号 + IP | 凭据验证失败 | 有上限、有到期时间的失败冷却 |
| 认证域 + 账号 | 跨 IP 的凭据验证失败 | 风险信号，触发验证码或 MFA，不直接禁用账号 |

认证域应区分管理员/会员及实际租户边界。账号规范化须与账号查找规则一致，不能擅自转小写造成不同账号合并。不存在的账号也须执行同样的计数策略，避免返回行为暴露账号存在性。

冷却期间立即返回 HTTP 429 与有效的 `Retry-After`，不使用长时间 sleep 挂住请求。已被拒绝、没有执行凭据验证的请求不新增密码失败次数，也不得无限续期当前冷却。

成功登录不增加失败额度，可清除当前账号/IP 的失败状态；不得顺便清空整个 IP 的请求额度或其他账号的失败状态。仍处于冷却或总请求限流期间的请求可以被拒绝，因此不承诺正确密码随时都能绕过限流。

“其他 IP 的失败不锁死账号”不等于完全无可用性影响：共享 NAT 的用户仍共享 IP 限额，账号风险升高会增加验证步骤。验证码/MFA 尚未实现时，不能把账号风险计数描述为已经具备跨 IP 防护效果。

P1 前账号风险阈值至少产生结构化安全事件，接入可配置的管理员告警出口；告警须聚合、去重、限频，不能让攻击者触发通知轰炸。告警不是自动阻断。固定窗口边界可能短时容纳接近两倍窗口额度，容量评估和阈值设计须覆盖该场景，不宣称任意滑动区间内都不超过该数值。

### 4.2 枚举防护

- 用户不存在时，也必须对预生成假哈希执行一次密码验证；算法与成本参数和正常密码策略一致。假哈希在初始化阶段准备，禁止逐请求重新生成。
- 禁用账号仍走等价的密码验证路径，拒绝签发会话。
- 不存在、禁用、密码错误对外使用相同状态码、错误码和文案；内部记录原因，禁止日志包含密码、验证码、令牌或完整敏感凭证。
- 假哈希降低时序差异，不保证端到端耗时恒等；存在历史哈希参数时须定义迁移与测试策略。

### 4.3 详细设计准入项

实施前的设计必须给出：各维度阈值、窗口、最大冷却、TTL、键规范、并发原子更新及清理语义、并行请求对失败阈值的影响、多实例共享存储、存储故障行为、配置变更和审计。不得在存储故障时静默无保护放行；拒绝或受限降级须明确且可验收。

账号计数建议使用服务端带密钥摘要，避免在缓存键与日志中暴露原始手机号/账号；同时限制恶意构造随机账号导致的键数量增长。具体实现留给 P0-b 详细设计。

## 5. P0-b：短信与恢复入口

短信须同时执行手机号、IP、全站三层发送额度，以及请求频率限制。成功发送必须消耗额度；不能只统计验证码校验失败或供应商发送失败。

发送前以原子操作预占额度，防止并发请求全部通过后再超发。供应商已接受或结果未知时不得直接退款；超时重试须有幂等和对账策略。只有明确未发送的失败才能按设计释放预占额度。

详细设计还须覆盖：手机号规范化、发送间隔、日预算、跨场景重复发送、验证码有效期/错误次数/一次性消费，以及多实例下同一发送操作只扣费和发出一次的边界。注册、短信登录、找回密码不能成为彼此额度的绕过入口。

### 5.1 短信/邮件验证码的独立尝试预算

当前 `MessageSendLogic` 比对失败直接返回 false，不计错误次数；成功后 get/delete 是分步操作。会员控制器还存在直接读 Redis 比对/删除的路径。P0-b 必须统一这些消费路径，禁止保留绕过共享校验服务的直接访问。

挑战绑定认证域、规范化接收人、用途和挑战标识（涉及绑定操作时还要绑定发起用户），不能只按手机号/邮箱保存裸验证码。错误预算按挑战共享，与请求 IP 无关；默认候选上限 N=5，详细设计可调整但必须固定有限值。第 N 次错误原子作废，之后正确代码也不能恢复旧挑战。

错误递增、阈值失效、有效期检查和成功消费必须为原子状态转换；并发正确请求最多一个消费成功。不同入口对同一挑战共用预算，轮换 IP、改用 validate 接口或不同业务场景不得绕过。重发使旧挑战失效，并受接收人/用途的滚动发送和尝试预算约束，不允许无限重发刷新猜测次数。

任何“先验证再提交”的流程须返回短时、用途绑定、一次性的业务凭证；不得只返回可复用的布尔成功状态，也不得使预校验绕过尝试预算。登录、换绑手机、绑定邮箱、重置密码均覆盖此契约。上述失败预算不意味着承诺无拒绝服务风险：攻击者可能消耗某个挑战，恢复通过受控重发而非重新启用旧码。

### 5.2 开发环境模拟通道（`security.verification.simulate`）

本地联调和 E2E 没有真实短信 / 邮件供应商，也不该为此配假模板。模拟通道让开发环境走**完整的发码与核验链路**，只是不真正投递。

**生效条件（启动时校验，fail-fast）。** `simulate = true` 只有在运行环境被**显式声明**为 `dev`、`local` 或 `test`（大小写不敏感）时才被接受。显式声明 = CLI `--env=<值>`，或环境变量 `NETON_ENV` / `ENV` / `NODE_ENV`（与 `ConfigLoader.resolveEnvironment` 同源同优先级）。以下任一情况 system 模块初始化直接抛错、进程拒绝启动：

- 环境为其他任何值（`prod`、`production`、`staging`……）；
- 没有显式声明环境 —— 框架此时默认解析为 `dev`，但这同样是生产机忘配 `NETON_ENV` 时的样子，不能据此放行。

选 fail-fast 而不是忽略并告警：忽略会让开发机上的每次登录都变成看不懂的 503，而生产机误开时宁可起不来也不能带着「不投递验证码」的配置上线。`simulate` 缺省或为 `false` 时不做任何环境要求。

**行为。** 模拟开启后，所有验证码（短信、邮件；会员与管理员两个身份域）：

1. 照常执行 §5 的冷却、每接收方日上限、全站日预算，照常写入统一挑战（同一 TTL、原子核验消费、5 次猜错作废）。模拟不绕过 `VerificationCodeService` 的任何一步。
2. **不调用任何真实供应商**，也不查模板 / 通道：即使库里配了模板或通道，模拟环境也只存不发，结果不随数据库内容变化。
3. 写一条 `verification.simulated` 日志，字段 `realm`、`purpose`、`channel`、`to`（脱敏）、`code`。这是全系统唯一允许把验证码写进日志的地方，前提是上面的环境校验已经保证它不可能出现在生产。
4. 把「该接收方最近一条模拟码」写入模拟收件箱（Redis `vc:sim:<channel>:<接收方>`，TTL 与挑战相同）。只是镜像，核验仍只认挑战本身；码被消费后收件箱里的旧码也无法再用。

**取码接口（仅模拟开启时可用）。** `GET /admin/system/dev/verification/latest?channel=sms|email&receiver=<接收方>[&realm=&purpose=]`：

- 需要管理员登录与权限点 `system:dev:verification:query`（超级管理员通配同样适用）。模拟未开启时恒 404，与不存在的路由不可区分。
- `receiver` 按发码时的规范形式匹配：短信为 E.164（URL 中 `+` 须编码为 `%2B`），邮件大小写不敏感。
- 返回 `{channel, receiver, code, realm, purpose, issuedAt, expiresAt}`；没有记录或 `realm` / `purpose` 与最近一条不一致时 404。

取码走接口而非固定验证码：固定码让任何知道它的人在模拟环境里登录任意号码，也让 TTL、一次性、猜错上限失去测试意义；接口保留随机码，读取受管理员认证、权限点、模拟开关、环境校验四道约束。E2E 也可以直接读 Redis 键，但键名是实现细节，接口才是稳定契约。

## 6. P1/P2 后续方向

### 6.1 风险驱动的人机验证

后端决定是否需要验证，返回供应商、公开站点 key、动作和挑战上下文。前端取得凭证后重新提交；后端核验成功、有效期、一次性、预期域名与动作，并绑定原业务用途。供应商能力不同的部分由适配器补齐，不接受仅前端验证通过的状态。

`system.security.captcha.*` 作为非敏感策略配置的候选命名空间，字段与现有设置机制对齐后再冻结。供应商 secret 只来自服务端环境/秘密管理设施；前端 env 只能包含公开信息。验证服务不可用时不能静默绕过已要求的验证。

优先评估 Turnstile；大陆用户场景同时评估当地可达的供应商。供应商选型需实测目标网络、审查数据处理要求；本文不冻结价格、可达性或默认供应商，不要求继续自研滑块。

### 6.2 管理员 MFA

优先设计 TOTP 和一次性恢复码，超级管理员强制策略须配套注册、恢复和紧急访问流程。恢复码仅存不可逆校验值，使用后失效。TOTP 密钥保护、时间窗口、重放防护和恢复操作审计须单独设计。Passkey 为后续扩展。

管理入口 IP 白名单或访问网关可作为附加保护，但不替代应用层登录防护。任何旁路入口均须纳入同等策略。

## 7. 自动化验收契约

Harness 每个场景必须有自动断言、隔离的计数命名空间及可重复运行的清理流程；不得通过打满线上公共额度进行验收。不同来源使用真实隔离连接来源/网络命名空间或可信代理测试桩，不能靠伪造外部 XFF 冒充两个真实来源。

| ID | 场景与自动断言 | 阶段 |
| --- | --- | --- |
| A01 | 两个不同解析客户端 IP 对同一路由请求，A 用尽额度后 B 仍有自己的额度；同一 NAT IP 的共享行为有明确测试 | P0-a |
| A02 | 外部伪造 XFF、X-Real-IP、多个头/多跳链，后端来源仍为预期真实客户端；覆盖直达后端代理及 Next.js 链 | P0-a |
| A03 | 缺头、全可信链、IPv4/IPv6、畸形/重复头有确定结果；即使入口未清理 X-Real-IP 默认也不采信；显式开启仅信任受控对端 | P0-a |
| A04 | 从外部网络验证实际后端/Next.js 端口不可直连；正常 Caddy 入口仍可访问 | P0-a |
| A05 | 验证发布版本、实际配置加载及最终分桶；伪造头实验使用实际站点配置，而非只依赖独立 Caddy 实验 | P0-a |
| A06 | 同一请求的限流、审计、网关白名单均使用同一只读来源值；覆盖有/无路由限流注解、全部适配器和配置冲突迁移 | P0-a |
| B01 | 密码哈希前总请求限流生效，成功请求也计入；不把总请求额度误当失败额度 | P0-b |
| B02 | 账号/IP 冷却有上限且到期后可恢复，被拒绝请求不无限续期；429/Retry-After 一致 | P0-b |
| B03 | 在总请求额度允许、组合冷却已到期时，正确凭据可成功；成功不增加失败次数，不重置无关计数 | P0-b |
| B04 | 不同 IP 对同一账号的失败不会修改另一个组合的冷却；账号级风险只升级验证、不禁用账号 | P0-b；验证分支需 P1/P2 |
| B05 | 不存在/禁用/密码错的对外状态码、错误码、文案一致，并确认都执行密码验证；受控环境统计时序分布 | P0-b |
| B06 | 成功短信消耗手机号/IP/全站额度；并发、超时、重复提交、供应商失败均不超发或不当退款 | P0-b |
| B07 | 多实例共享额度、TTL 到期、存储故障、配置更新均符合已评审设计 | P0-b |
| B08 | 同一短信/邮件挑战跨 IP 累计错误，第 N 次作废，随后正确码仍失败；跨入口共用预算，并发成功仅消费一次，重发不恢复旧码 | P0-b |
| B09 | 有效路由元数据 gate 覆盖所有匿名认证及验证码入口；明确测试 login-username/register、换绑/邮箱/重置路径的限流与哈希前拦截 | P0-b |
| B10 | 跨 IP 风险事件可观测且告警限频；固定窗口边界突发符合容量预算 | P0-b |
| C01 | 缺失、伪造、过期、重放、错域名/动作的挑战凭证被拒绝；前端关闭开关不能绕过 | P1 |

时序验收不使用“单次耗时相同”断言。P0-b 设计需预先固定测试环境、样本量、预热、统计指标及允许差异，保存分布结果，避免凭手工观察宣称消除了枚举。
