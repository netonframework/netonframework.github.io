# 国际化（i18n）：服务器与客户端协同

状态：生效（2026-11-03）。来源：DeviceAdmin 与 Neton Application 协同 i18n 架构评审（两轮对抗评审）。

本文规定 Neton Application 作为脚手架标准的多语言协同契约：谁保存用户偏好、每次请求为谁选择语言、谁负责翻译。
身份域隔离见 [identity-realm.md](identity-realm.md)；语言枚举与读取契约见 `contract.core.UserLanguage`
与 `contract.core.UserLanguageReader`（由 module-account 在 `AccountRuntimeBootstrap` 绑定）。

## 0. 目标与反目标

- **目标**：站点默认语言只是兜底，不是「所有用户都应该用的语言」。一个已登录用户明确选择了语言后，
  刷新页面、换设备登录、调用个人 API、收到发给他的通知，都应得到一致且可解释的结果。
- **反目标（明确不做）**：
  - **不做后端 API 错误信息多语言化。** 错误契约与用户语言是两件事，程序按稳定错误码判断发生了什么。
  - **不把语言固化进 JWT。** 令牌只证明「是谁」；「这次用什么语言」由应用在认证后解析。
  - **不要求每个 fork 再建一个语言字段、再写一套优先级。** 要标准化的是下面这些**可观测行为**。
  - 内部系统（不做 SEO、私有响应走 cookie 会话、无共享缓存）**不引入 `Content-Language` / Vary 缓存协商**。

## 1. 三句话核心契约

> **偏好跟人 · 语言跟请求 · 通知跟收件人。**

| 场景 | 规则 |
|---|---|
| 已登录的个人界面、个人 API | 从已验证的 `(realm, subjectId)` 读取用户**明确保存**的偏好；未设置时才用当前客户端语言偏好，最后回退站点默认。浏览器自动上报的语言不能覆盖用户主动保存的选择。 |
| 未登录、登录失败、MFA 挑战 | 用登录页用户主动选择的语言 > `Accept-Language` > 站点默认。**不得按「尝试登录的用户名」查询语言**，否则错误响应的语言本身就可能泄露账号是否存在。 |
| 公开文章、SEO、RSS、站点地图 | 由公开路由或发布版本决定语言；没有多语言版本时用站点发布语言。不因访问者已登录就悄悄改变同一公开 URL 的内容。界面语言 ≠ 文章已被翻译。 |
| 邮件、短信、推送、站内通知 | 按**收件人**及该渠道支持的模板语言选择，而非操作人或后台任务所在机器的语言。英文管理员触发给中文用户的操作，用户应收到中文。重试同一封已生成内容时不改变语言或模板版本。 |
| 机器 API Key、系统任务 | 无自然人身份即无「用户偏好」。有明确接收方按接收方；否则按接口约定或客户端协商。**不得把 API Key 编号当作 account 用户 ID。** |

「拿这个用户的 token 调 API 就知道该给他哪种语言」可以实现，且 **token 里不需要 `language`**：认证后解析一次、放入请求上下文、同一请求只解析一次，不让每个业务模块各查一次库。

## 2. 身份域与存储

按 [identity-realm.md](identity-realm.md)：管理员（`system_users`，module-system，`realm=admin`）与终端用户
（`account_users`，module-account，`realm=account`）是**不同主体**，数值 ID 可以相同。二者语言偏好的存储实现不同，
都**不冗余**：

| 域 | 存储 | 写入接口 | 值形状 | 读取方 |
|---|---|---|---|---|
| account（C 端） | 通用账户偏好命名空间 `app.language`（`UserLanguage.PREFERENCE_NAMESPACE`） | `PUT /app/account/preferences/app.language`（乐观并发 `version`） | **JSON 字符串标量**（如 `"en-US"`），不是对象 | `UserLanguageReader`（`UserLanguage.of(content)`） |
| admin（后台） | `system_users.locale` 列 | admin 自助资料更新接口 | 同上语义的 BCP 47 标签字符串 | 需 admin 侧对等 reader（见 §3） |

规则：
1. 按 `(realm, subjectId)` 定位偏好；**相同数字 ID 不得跨域串语言**。
2. 不让 account 专用 `UserLanguageReader(Long)` 同时解释两套用户 ID。需要跨域读取时，提供带身份域的主体引用，或由装配层按域委托两个 reader。
3. 业务模块拿到的是「当前请求语言」或「目标收件人语言」，不需要知道偏好存在哪张表。

## 3. 当前请求语言（需要补齐的一环）

`UserLanguageReader` 的签名是 `language(userId: Long): UserLanguage?`，**按 userId 查账户偏好并返回可空结果**——它不是会话字段，也不是请求语言上下文。落地要求：

1. 认证后，在**请求内解析一次**「当前语言」并复用；结果优先级 = 用户明确偏好 > 客户端语言 > 站点默认。
2. 需要「当前请求语言」的调用方复用这次解析，**不各自打库**（否则一封通知渲染命中 N 次偏好查询）。
3. 缺省值不由业务模块各自硬编码 `UserLanguage.DEFAULT`；由产品的站点默认策略统一决定。
4. 用 session/Redis 加速时，缓存是偏好的**副本**：写成功必须更新或失效它；**不得让 JWT 到期时间决定语言切换何时生效**。
   验收底线：**用户从英切中后，用原 access token 的下一次请求即按新偏好处理**，无需重登、刷新或撤销其它设备会话。
5. admin 侧目前无对等 reader（`system_users.locale` 只被读回给前端做界面渲染）。要让「服务端写给管理员的文本」跟随语言，须补一个按 admin 主体解析请求语言的 reader。

## 4. 谁翻译：一种内容只指定一个主要翻译方

- **交互式界面**：API 返回稳定业务错误码、字段路径与结构化参数；**前端**用模块词条翻译。自家前端按当前语言渲染菜单、控件、页面文案。
- **服务端主动写给用户的文本**（邮件、短信、推送、站内通知）：由**服务端模板**渲染，按 §1 收件人语言选择模板语言。模块拥有模板与参数定义，公共 runtime 负责语言匹配、回退与缺词观测；**不在业务逻辑里到处写 `when(language)`**。
- **站内通知的存储策略**（须按通知类型**声明**其一，两种都合理但不能含糊）：
  - 希望旧通知随界面切换 → 存「消息键 + 参数」；
  - 希望保留当时送达的确切文本 → 存「渲染快照 + 语言 + 模板版本」。
  - 用户原创内容保留原文，不因切换 UI 语言自动改写。

## 5. API 错误：不本地化

- 后端 `message` 可以**始终一种默认语言**，不必查询用户偏好，也不要求每个错误码有译文。
- 客户端按**稳定错误码**判断业务分支，**绝不比较 `message` 文本**（中/英句子都可能变）。
- 需要引导用户操作的场景（登录失败、会话过期等），**前端可按错误码显示当前语言的本地操作提示**；未专门处理的错误显示通用提示并附错误码。这是界面体验，不是后端翻译义务。
- 错误接口唯一要验证的行为：**切换语言不改变同一错误的业务码与 HTTP 状态**。

## 6. 语言匹配规则（单一事实源）

前端与后端必须对同一语言标签选出**同一个语言包**，否则「即使库读写都对，用户仍可能看到简体界面、收到繁体通知」。

1. 规则：**精确匹配 → 文字体系（script）→ 受控别名表 → 最终回退**。有显式脚本（`zh-Hant`/`zh-HK`）时**优先尊重脚本**，不按 supported 数组顺序猜测。
2. `Accept-Language` 是带权重的偏好**列表**，不是一个可以直接传给 `UserLanguage.of()` 的字符串。
3. 匹配语义遵循 [RFC 4647](https://www.rfc-editor.org/rfc/rfc4647)；HTTP 语言协商遵循 [RFC 9110 §12.5.4](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.4)。
4. **Kotlin 与 TypeScript 共用同一批匹配测试向量（黄金用例），不要求共用实现**——用同一批用例锁死两端结果一致。`zh-HK` 在 `[zh-CN, zh-TW]` 下须两端都选 `zh-TW`。
5. 区分三件事，不互相改写：
   - **用户偏好标签**（可为 `en-GB`）；
   - **服务端实际取用的语言包**（暂时只有 `en` 模板也合法，不回写用户的 `en-GB`）；
   - **格式化 locale**（前端仍可按 `en-GB` 排日期/数字）。
   - 时区、币种**不得**仅凭语言推断。
6. `contract.core.UserLanguage` 现有五值（zh-CN/zh-TW/en/ja/vi）继续表示**内置服务端文案语言**，但不宜永久规定所有 fork 能支持哪些界面语言。

## 7. 发行版声明支持哪些语言

- 「支持哪些语言」与「默认显示哪种语言」是**两份配置**：
  - `supportedLocales`（可选语言集合）来自站点配置 + 构建期环境（如 `site.generated.ts`）；
  - 运行时后台「站点语言」提供的是**默认语言**，不是可用语言包清单。
- **只把实际具备核心界面词条与模板覆盖、并通过验收的语言，声明为该发行版支持的语言。**
- 改后台默认语言 ≠「已经支持繁体」；上新语言 = 加词条 + 加模板 + 过匹配测试，而不是改一个默认值。

## 8. 模块登记（渐进迁移）

新增模块承诺 i18n 时登记：词条命名空间、各语言 key 与 `{参数}` 对称、模板语言覆盖、缺词回退声明。
`check-locales` 类门槛只扫「已声明 `locales` 的模块」，未声明模块仅告警不阻断，允许按模块逐个迁移、已迁移的不许倒退。

## 9. 前端 runtime 职责

- 登录态 bootstrap / 当前用户响应应同时给出**保存的偏好**与**本次生效语言**；SSR `<html lang>`、首屏词条与客户端首帧使用同一结果。
- `localStorage` 只服务匿名体验与切换加速，**不得成为登录后的第二份权威**；尤其不得让同一浏览器上一个账号的选择覆盖下一个账号。
- 界面切换与偏好持久化是**两件事**：切换成功不等于保存成功。保存失败可保留本机显示，但须提示或回滚，不能当成「已同步到账户」。
- **登录态变化（登录/换号/登出）须重新读取新主体偏好，并丢弃上一账号尚未返回的读取结果**；若根 Provider 跨客户端路由不重挂，不能假定偏好会自动加载。
- 写入走各域接口：account 用 `PUT /app/account/preferences/app.language`（带 `version` 乐观并发），admin 用自助资料接口。并发用 `version`，不静默覆盖另一设备刚保存的偏好。

## 10. 验收三阶梯（各自证明不同的事）

| 阶梯 | 证明什么 | 关键用例 |
|---|---|---|
| **① 存储接通** | 偏好读写到正确的键、值、版本，reader 能解析 | 用已有 token PUT 再 GET `app.language`（验带点 `{namespace}` 路径不被截断、值为 JSON 字符串、`version` 生效）；再用**实际绑定的 reader 断言 `en-US` → `UserLanguage.EN`**。只用 curl 读回 `"en-US"` **不能**证明 reader 已接通。点路径失败应修路由/代理，不退回 list 接口绕开契约。 |
| **② 界面与请求跟人走** | 当前语言随认证主体解析并驱动界面与请求 | 匿名→登录、同浏览器 A 换 B、跨设备、保存失败、同 ID 的 admin/account 不串语言；用原 token 发起下一次**确实需要语言**的请求，观察其采用新偏好（不拿错误文案当探针）。 |
| **③ 服务端输出跟收件人走** | 发给用户的内容按收件人语言渲染 | 选一种真实通知：英文管理员触发、中文收件人收到中文；发送重试遵守该通知类型声明的语言与模板策略。 |

四条脚手架达标的底线：**旧 token 切换语言立即生效；同 ID 的 admin/account 互不串语言；英文管理员触发的通知按中文收件人渲染；`zh-HK` 在前端、SSR 与服务端选中一致。** 最后一条在发行版真正上线繁体时才可达，届时以 §6 的共享测试向量前置拦住分叉。

## 11. 落地顺序

1. **DeviceAdmin fork 先修第一步**：C 端把 `locale` 命名空间收敛到 `app.language`（值形状已对，不动）；旧键若从未上线直接删错误实现，有数据只在新键缺失时迁移、不长期双写。**注意 admin 壳的界面切换/加载缺陷与 C 端镜像，须两壳同修（§9）。**
2. **规范与请求语言上下文**：把 reader 包成请求级「当前语言」，覆盖匿名登录、已登录 bootstrap、手动切换、SSR 首屏、旧 token 续用。
3. **一个收件人场景 + 一种通知类型做端到端样板**：建立词条命名/参数一致/缺词回退与敏感信息检查，其余模块按样板接入。

第一步是 DeviceAdmin 的修复；第二、三步才是上游脚手架可复用的能力。
