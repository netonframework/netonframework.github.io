# Neton 1.2.0 TODO：可验证的多系统协作底座

> **Draft r6 · 2026-11-26 · 待评审，不是已实现能力或发布承诺。**
>
> 本次核对的框架源码 `gradle.properties` 为 `1.1.2`；本文规划目标为 1.2.0，不修改版本号、不启动发布。所有 TODO 都必须经过实现、测试和证据审查才能标为完成。涉及现有冻结契约的变化，先修订对应规范，不能凭本草案覆盖它们。

## 1. 定位与取舍

1.1.x 已具备 HTTP、WebSocket、安全、数据访问等网站应用基础。下一阶段重点不是继续堆入口语法，而是让单体、模块化单体和多系统部署具有一致的生命周期、资源约束、故障恢复与诊断能力。

“可覆盖几乎 99% 网站应用”作为产品方向理解，不作为统计结论；“Spring Boot 能做的都能做”也不能替代逐项能力、平台和运行验证矩阵。现有功能可用不等于所有分布式故障路径已得到验证。

**设计原则：**

- 普通 Kotlin 函数、接口、数据类型优先；注解只承担编译期声明，不增加第二套业务执行语义。
- 编译期能发现的装配错误前移；网络、身份、租约、运行期配置仍必须在运行期验证。
- 默认单进程可用。启用分布式能力才引入对应依赖、后台任务和持久化设施。
- 每项能力写清所有者、状态机、资源上限、失败与取消行为；不用“自动”“透明”掩盖不确定结果。
- AI 友好意味着机器可读契约、源码定位、确定性测试和小范围修改，不是新增提示词 DSL 或让模型参与运行时决策。
- 高性能与安全、正确性同时验收；不能删掉准入、鉴权或恢复逻辑换取跑分，也不承诺未经验证的零开销。

## 3. 架构边界

```text
业务应用 / 模块化单体 / 独立服务
  普通业务函数、领域授权、事务、补偿与对账
                 |
可选协作能力
  服务客户端 + 发现 SPI + 调用策略
  可靠事件 + Inbox / Outbox 适配 + 可选 Saga
                 |
共同底座
  生命周期、调用上下文、契约清单、诊断 SPI、资源预算
                 |
现有 HTTP / RPC / WebSocket / DB / IO 实现

外部基础设施：DNS / 注册中心 / 消息系统 / 网关 / Service Mesh
```

模块名称与接口签名尚未冻结；一致性模块的推荐命名与拆分见 §8.3。不预先创建一批空模块；按独立依赖、生命周期和测试边界决定拆分。HTTP 与 msgtrans 可复用调用策略契约，但不能被强行包装成丢失流式、取消和错误语义的万能传输接口。

## 4. 编译期架构与 API 契约（P0）

### 4.1 应用装配清单

- 输出版本化、确定性排序的机器可读清单：模块、依赖、公开入口、路由模板、身份域、权限声明、Job、事件监听者、引擎能力及配置 schema。
- 每个条目关联源码位置、生成器版本、构建版本和契约摘要。生成源码可阅读、可调试，禁止仅靠运行期注册顺序解释行为。
- CI 检查重复路由、缺失组件、循环依赖、未满足能力及契约不兼容变化；不把密钥、真实配置值或用户信息写入清单。
- `@Module` 的依赖声明与 Gradle 可见性、静态规则配合。KSP 不能单独证明任意函数体没有越界访问，不能宣称已完成全程序架构验证。

### 4.2 一个契约来源，多个产物

- 从路由、DTO 和序列化规则生成 OpenAPI、客户端契约与兼容性报告；不维护相互漂移的三份定义。
- 自定义 serializer、泛型、多态、可空与默认值必须有明确支持矩阵；无法准确推导时要求显式 schema 或报错，不静默生成错误文档。
- 运行期继续验证不可信输入。生成客户端不等于服务端可以跳过参数检查或授权。
- 新增能力尽量复用现有 DSL/KSP 入口；不为 CQRS、重试或追踪增加另一套 Controller 编程模型。

## 5. 可追溯、可调试与 AI 开发（P0）

- 统一关联 buildId、routeId、traceId、operationId、attemptId、eventId；明确每个 ID 的生命周期，不把 WebSocket connectionId 当登录会话 ID。
- 错误保留机器码、阶段、原因链与是否可重试；取消不是普通业务失败，不吞掉取消继续重试。
- 定义轻量诊断 SPI；OpenTelemetry 导出作为可选适配，不把具体后端绑进 core。语义约定锁定版本，实验字段不直接成为稳定公共 API。
- metrics 使用有界低基数标签；用户 ID、URL 原文、调用 ID 不作为指标标签。日志和 trace 默认不收正文、凭证、签名、Cookie、SQL 参数或 AI 提示内容。
- 诊断区分排队、连接、TLS、首字节、handler、写出、关闭。HTTP dispatcher 完成不能标成网络写出完成，WebSocket 握手结束不能标成连接结束。
- 提供受保护的装配/配置来源/能力诊断快照和构建信息；禁止公网默认开放任意执行、内存转储或密钥查询接口。
- CI 产出可供人和 AI 读取的失败报告：测试场景、源码位置、构建摘要、脱敏输入、预期/实际状态、复现命令。网络录制默认关闭，样本必须脱敏。

验收：未启用导出器时不创建后台导出线程或无界队列；启用后导出阻塞不能阻塞 reactor；抽样、队列容量、丢弃计数和退出时限可测。

## 6. 生命周期与调用预算（P0）

- 定义逻辑操作总期限和单次 attempt 期限，排队、发现、建连、退避、读取均计入总预算；禁止每层重新获得完整超时。
- 本地耗时用单调时钟。跨机器传播剩余预算或受限制的期限，接收方按本地策略截断，不直接比较不同进程的单调时间戳，也不信任客户端无限期请求。
- 请求子任务受结构化并发管理。需要脱离请求存活的工作必须交给显式、受生命周期管理的后台组件或持久队列。
- readiness 与 liveness 分离。下游故障通常影响就绪/降级，不应无条件触发进程反复重启。
- 停机顺序明确：停止准入/撤销就绪，通知发现设施，排空已有工作，期限到后取消并释放资源。不能依赖注册中心立即传播摘除信息。
- WebSocket、流式响应、事件投递和 Saga 各自定义 drain/恢复策略；无法及时撤销的远端副作用记录为结果未知，不能伪装成本地取消成功。

## 7. 服务发现与可靠调用（P0）

### 7.1 最小发现能力

目标是“多个系统能稳定互相找到并调用”，不是自研 Eureka、Consul 或 Kubernetes。

- 提议逻辑服务标识、不可变 endpoint 快照、解析/订阅 SPI，首批提供静态部署配置与 DNS；选一个真实部署场景验收，其他注册中心按需加适配。
- 快照记录来源、版本、有效期、权重及可用状态。更新整体替换；刷新 single-flight，避免每个请求都访问注册中心。
- 规定空集合、首次不可达、失效、乱序更新和断网行为。最后可用快照只能在显式、有上限的 stale 窗口内使用；超期失败，不无限缓存旧节点。
- 注册与解析分离。服务注册是可选生命周期组件，拥有租约续期、失败状态和退出清理；不默认开放注册中心写权限。
- 实例标识、地址、逻辑服务名分离；池连接退役须有界且不立即杀死正常在途请求。TLS 验证使用正确的服务身份/SNI，不能因解析为 IP 就关闭证书校验。
- 不接受外部请求任意指定注册中心、目标服务或内部地址；部署信任与租户权限显式建模，遵守既有 egress 契约。

### 7.2 负载均衡与故障策略

- 每一跳的同一候选实例集合只有一个明确的负载均衡责任方：应用、网关或 mesh；不同跳可以分别选择实例。端到端重试预算另行统一，不能由此推断整条链只允许一个代理。首批默认简单轮询；是否增加延迟感知算法由测量决定。
- 可选隔离、限并发、限排队、熔断、退避抖动与重试预算。状态按服务/操作有限划分，不能按任意 URL 永久增长。
- 默认不自动重试有副作用的请求。仅在操作幂等、具有可验证幂等键或能证明尚未提交时重试；断连不代表远端没执行。
- 流式响应开始交付后不透明切换上游；请求体不可重放时不自动重试。网关与客户端不得各自无限叠加重试。
- 不用全局热锁统一维护所有请求；先定义准确语义，再按连接、服务或 worker 分片。优化不能放宽实际全局上限。

验收：新增/摘除节点、DNS 变化、快照过期、TLS 身份不符、连接池退役、下游变慢、请求取消与恢复风暴都有确定性测试。

## 8. 分布式事务：可靠一致性，而非透明远程 ACID（P0 / P1）

| 场景 | 推荐方案 | 明确不保证 |
|---|---|---|
| 同一数据库内的业务变更 | 现有本地事务 | 不跨网络延伸 DbSession |
| 本地提交后可靠通知另一个系统 | 同事务 Outbox + 至少一次投递 + Inbox/幂等消费 | 不保证只投递一次 |
| 多服务业务流程 | 持久化 Saga、幂等步骤、补偿、对账 | 补偿不是物理回滚，不提供全局隔离 |
| 必须跨资源强原子性 | 先收敛事务边界；确有需求时独立评审 XA/2PC/TCC | 1.2.0 不默认实现通用事务协调器 |

### 8.1 必做的可靠交付闭环

- 复用已有 outbox 端口。业务更新与事件记录在同一数据库事务提交，不允许先 commit 再“尽力发消息”冒充可靠通知。
- 消费端 Inbox 去重记录与本地业务更新原子提交；唯一键包含来源/租户、消费者和事件 ID，不能只靠进程内缓存。
- 若副作用在外部系统，使用对端幂等键或持久状态加查询/对账；本地 Inbox 无法把外部调用变成恰好一次。
- 保留 claim/fencing 语义，过期 worker 不得覆盖新 worker 状态；重试有上限和持久失败状态，人工恢复有授权与审计。
- 明确去重保留期与最大重放窗口，过期事件的恢复方式；不能清理去重记录后仍承诺无限期幂等。
- 事件 schema 版本、未知字段、旧消费者、毒消息、积压、死信和清理策略形成验证矩阵。需要顺序的业务明确分区键/序列号，不承诺全局有序。
- 框架定义端口与一致性测试；持久化适配可选，表迁移仍显式执行，不在应用启动时自动改生产库。

### 8.2 Saga 候选能力

使用普通 Kotlin 步骤处理函数与显式状态机，不设计隐式跨服务 `@Transactional`。

持久记录流程版本、步骤 ID、幂等键、输入引用、状态、期限和补偿进度。步骤执行与结果落库间崩溃属于必须测试的“不确定结果”，依靠幂等或查询恢复。定时器可恢复，不以常驻协程代替持久状态。

补偿可能失败或不可逆；必须有退避、最终失败、人工介入和对账路径。流程升级时旧实例继续按固定版本执行或显式迁移，禁止部署后悄悄换步骤含义。

首个验证流程采用订单/库存/支付三个独立测试服务，覆盖提交成功但响应丢失、重复执行、重启恢复、补偿失败。具体业务规则不进入框架。通过前 Saga 不声明生产可用；“完整一致性套件”的交付必须连同 §8.3–8.9 全部验收，不能用前置模块完成代替整套完成。

### 8.3 模块命名：一致性基础 + Saga，而不是万能事务包

推荐总能力名为**可靠分布式协作（持久执行与一致性）**，框架模块采用以下候选方案。完整是指明确范围内的业务闭环完整，不是实现所有事务算法。

| 候选模块 | 职责与依赖 | 不负责 |
|---|---|---|
| `neton-durable` | 持久工作、交付/恢复状态机、消息信封、幂等与存储/传输 SPI；依赖现有 neton-database，在内部提供可选数据库存储与事务桥 | 不直接引入第二套驱动或 broker；不拥有业务表或业务补偿；不提供任意代码重放 |
| `neton-saga` | 依赖 durable；版本化流程、步骤、补偿、持久期限、查询与恢复操作 | 不实现 XA，不提供透明跨服务 `@Transactional`，不新造消息总线 |
| durable 的传输适配 | 按需独立交付 HTTP/msgtrans 或 broker 接线；首版选择一种并完成端到端验收 | 不把所有 MQ 客户端捆进核心；不重新实现消息 broker |

先按职责分包，只有独立依赖/生命周期需要才拆产物；不为 Inbox、Outbox、每种状态各造一个小库。测试套件作为可复用 testkit 交付，不随生产依赖装入。

**r5 模块决定：不建立独立 `neton-durable-postgres` 产物。** 数据库存储与事务桥放在 durable 内部的 storage/database 实现分包，PostgreSQL 作为首个通过真实测试的方言。依赖方向为 `neton-saga → neton-durable → neton-database → core`，database/core 不反向依赖 durable。应用安装 durable 时显式选择存储和数据库资源；未选择数据库存储就不为 durable 自动建池、连接、迁移或启动扫描任务。启用生产持久执行却没有可用持久存储时失败，不降级内存。

“可选”指运行时选择，不承诺构建依赖消失：当前 `neton-database/build.gradle.kts` 按构建属性选择单一原生 driver，durable 沿用它，不另拉 PostgreSQL driver。其他方言可编译不等于 durable 存储契约已支持；能力未验证时拒绝选择该后端。公开消息/Saga 类型不暴露驱动类型，显式事务桥可使用已有数据库抽象。验收需包含非 PostgreSQL 构建不重复链接驱动、禁用 durable 数据库存储无额外连接，以及无数据库参与者的 API 编排场景。

`neton-durable` 表达“进程退出后可恢复”，取代 r3 较长且容易承诺过多的 `neton-consistency`。不选 `neton-box`：名字不能表达交付语义；不选 `neton-state`：容易与通用状态管理/缓存混淆；不选含糊的 `neton-transaction`：容易被理解成现有本地事务或全局 ACID。`neton-saga` 名称准确，但单独使用不足以涵盖可靠消息和幂等基础。以上是候选名，未创建产物或冻结包名。

**与现有规范的显式演进点：** [event v1](./event.md)目前规定投递器、存储实现与运维属于应用层，并不支持跨进程广播。本方案提出将新的通用一致性机制放入可选框架模块，属于需评审的边界变更；本草案不立即覆盖旧规则。实施前必须修订对应契约，说明新模块与旧 `DomainEventStore` 的桥接方式、表所有权、迁移和兼容测试。旧表不直接接管、不直接重命名；现有应用和 core 无需启用新模块。

若提取应用层通用实现进入官方适配，必须先剥离业务身份、权限字符串和运维路由；应用仍负责权限策略、数据库配置、显式迁移和运维入口。启动检查所需能力是否具备；每次事务桥调用还须校验当前事务属于同一资源/会话，不能只靠启动成功证明同事务。无事务、错误数据库、会话已结束时拒绝调用，禁止隐式另开事务或降级成内存队列。

#### 数据库是否必须联动

**Saga 不要求适配所有参与者的数据库，但可靠恢复需要持久记录；本地业务写入与通知原子性则需要参与者自己提供事务桥。** 两者不是同一个问题。

| 用法 | 所需能力 | 责任边界 |
|---|---|---|
| 编排多个外部 HTTP/RPC API | 协调器持久存储 + 参与者幂等/查询协议 | 无需连接参与者数据库；业务定义动作和补偿 |
| 本地订单提交后必须发事件 | 业务写入和 Outbox 同一事务，或已证明的等价日志机制 | 应用选择原子范围，框架事务桥复用现有 DbSession；不能另用独立存储做双写 |
| 消费消息并修改本地业务数据 | Inbox 完成状态和业务更新同一事务 | 应用提供处理函数，存储桥保证提交边界 |
| 参与者为第三方支付系统 | 对端幂等键、权威状态查询、对账或人工处置 | 框架不能从自己的日志推断对端数据库结果 |

持久存储 SPI 定义原子状态迁移、条件写入、租约和扫描能力，不暴露 JDBC/SQL/驱动类型。关系数据库、可靠日志等均可实现，但必须通过契约测试；内存实现只用于测试。PostgreSQL 是首个验证后端，不是全局最佳方案或强制部署要求。

同一个 PostgreSQL 适配可以同时提供协调器存储与本地事务桥，但不同连接池/数据库不能因为都是 PostgreSQL 就宣称原子。协调器存储可以独立部署；业务 Outbox 必须留在业务自己的提交边界内。业务团队决定“哪些更新需要联动”，框架提供通用可靠机制，不能要求每个业务重新实现 claim、去重和崩溃窗口。

#### 复用与所有权

- core 的 `DomainEventBus` 保持进程内语义。显式事件桥把选定事实转为集成事件，不能同时由旧投递器与新 durable worker 接管同一记录。
- DbContext/DbSession 仍是唯一数据库执行入口；适配不得直接持有业务驱动或跨事务保存会话。同步监听者只有在同一实际事务中才具有原子性，不能由“同步调用”推导跨库原子性。
- durable 拥有持久重试、到期扫描和 claim；现有 jobs 可以触发唤醒，但不是第二个状态权威。服务关闭先停止新 claim、等待 worker 退出，再关闭存储与客户端。
- 可靠客户端只处理一次持久 attempt 内的网络行为。默认关闭其额外自动重试；显式开启时纳入统一次数与期限预算，保留同一幂等键，不能与持久重试相乘而失控。
- Saga 拥有流程与补偿决策；durable 不认识订单/库存含义。HTTP/msgtrans/MQ 适配只运送消息，不自行决定业务完成或补偿。

### 8.5 与分布式事件分发的关系

统一的是**持久身份、交付、幂等、恢复和观测契约**，不是把命令、事件、工作流混成一个万能消息对象。

- 领域事件是进程内业务事实，保持现有总线语义；只有显式选定的集成事件进入跨服务传输，不能自动把全部领域对象序列化上网。
- 集成事件陈述已经发生的事实，可被多个独立消费者消费；命令要求目标执行动作，有明确结果/拒绝语义。Saga 通过命令与结果推进，不能把 broker ACK 当业务完成。
- Outbox 是发送事务桥，Inbox 是消费事务桥；broker/HTTP/msgtrans 是传输，不负责业务事务。CQRS 投影和 Saga 都使用同一可靠交付基础，不各建一套重试/租约逻辑。
- 信封包含稳定 messageId、类型与 schemaVersion、可信来源、租户作用域、correlationId/causationId、生成时间及可选业务序列号。traceId 不能替代幂等键；重投保持 messageId，不生成“新事件”逃过去重。
- 每个消费者独立记录处理结果；扇出中一个消费者失败不把其他消费者已提交结果回滚。新增消费者是否回放历史必须显式配置，不能依赖当前监听列表推断历史收件人。
- 顺序仅在声明的聚合/分区范围保证；幂等不解决乱序。缺口、陈旧版本和冲突由版本检查及恢复策略处理，不宣称全局有序。
- 远端信封的租户和来源须经认证绑定与授权核验，不能直接信任请求字段；消息大小、schema、订阅目的地及重放操作受限。

```text
A 本地事务：业务更新 + Outbox
                ↓ 提交后投递（允许重复）
B 本地事务：Inbox 唯一性 + 业务更新 + 可选下一条 Outbox
                ↓ 提交后确认
Saga：持久步骤/补偿状态 + 待发送命令原子记录，接收结果驱动下一步
```

Saga 状态与消息意图必须能在同一持久事务提交；不同数据库的双写不满足此契约。若适配无法保证，必须使用单一权威记录加可重建投递机制，并单独证明崩溃恢复；首版不支持任意跨库组合。

### 8.6 Outbox、Inbox 与幂等的精确边界

**Outbox：** 发送记录与业务变更复用同一个 DbSession/事务。提交后 worker 用短事务 claim，在数据库事务外执行网络发送，再以 claim token 条件更新结果。传输持久接收与最终消费完成分开记录；发送成功后本地确认丢失会重发，因此只能承诺至少一次。首版明确轮询批次、并发、积压容量与退避上限。

**Inbox：** `(可信来源, 租户, 消费者, messageId)` 唯一约束保证接收身份不重复，业务 operation 的完成状态与业务更新同事务生效；接收身份存在本身不证明业务执行过，不能靠“先查再写”判断。处理失败回滚本地效果。同步处理模式在业务提交后确认；异步接收模式先持久保存完整载荷/有效引用和待处理状态，才返回 RECEIVED，随后由可恢复 worker 执行“业务更新 + COMPLETED”事务。重复收到 RECEIVED 不能被当成已处理而删除；先 ACK 再只在内存排队不合格。外部调用不能长时间占着此事务，转为持久外部步骤执行。

协议明确 RECEIVED、COMPLETED、REJECTED、UNKNOWN 的含义与关联操作 ID；传输成功最多按适配声明证明持久接收。Saga 等待业务结果，结果消息本身也必须可靠投递或可查询。相同消息身份还绑定载荷摘要，重复身份但载荷变化隔离报错；接收方在转换之前核验稳定摘要，不能因 codec 升级误判为新消息。

**请求幂等：** `(租户/主体授权范围, 操作及版本, idempotencyKey)` 绑定版本化的规范化请求摘要；同键不同输入拒绝。摘要包含影响副作用的参数，不包含随机 traceId。每次命中仍须鉴权，不能向其他主体返回旧结果。结果只保存有界、允许重放的业务输出，不持久化凭证。

状态必须区分处理中、成功、确定失败、结果未知。处理中可返回操作句柄或有界等待；成功复用结果；瞬态失败允许继续同一操作，不能换键重复执行；未知先查证/对账。租约过期只说明 worker 失去所有权，不证明外部操作没执行。

幂等记录保留期不得短于允许的自动重试/重放窗口。过期后的历史消息不能默认为全新请求执行；必须拒绝、隔离或走有审计的人工恢复。大结果和大消息使用有生命周期的外部引用，并验证访问隔离和保留期，不能靠无界数据库正文规避内存限制。

**保留期必须可执行：** 完全删除去重记录后，仅凭任意客户端键无法区分“旧键重放”与“首次调用”。首版使用受信任发行方绑定的期限/命名空间代次，结合保留的去重墓碑或关闭代次的拒绝规则；不信任任意客户端时间戳。普通外部幂等键只承诺明确的保留窗口，过期操作的自动恢复必须停止并进入查询/人工处置。未结束 Saga 的键与对端去重期限一起检查，不能在对端已忘记旧键后自动重试扣款。

COMMIT 成功但连接断开可能导致调用方不知道提交结果：应按稳定 operationId 从权威存储查询，不以超时推断回滚，不生成新键重试。能力无法证明同事务时不得声明本地效果去重保证。大载荷引用先完成持久写入再记录可投递消息，失败产生的孤儿受有界 GC 管理；消费仍引用的对象不得提前清理。

### 8.7 恢复、租约与运维

- 持久化 attempts、nextAttemptAt、owner/claim token、期限和最后失败分类；进程内定时器只是唤醒优化。重启扫描能找回到期工作，运行期等待用单调时钟，持久租约采用适配定义的一致时钟来源与偏移策略。
- 所有 claim 更新使用条件写入；过期 worker 的迟到完成不能覆盖新 owner。数据库 fencing 不会自动阻止外部副作用，外部动作仍需对端幂等键、fencing 支持或结果查询。
- 失败分类区分可重试、永久失败、未知结果、需人工介入。重试耗尽必须进入可查询状态；不是无限重试，也不是删除失败记录。
- 死信/隔离、重试、暂停、恢复和对账属于完整交付的一部分，须鉴权、审计并再次校验版本与幂等范围。人工“标记成功”必须记录证据，不能无条件跳过业务不变量。
- 存储满、broker 长期故障或积压超限时拒绝新的可靠工作，不能成功返回后丢弃。所有可靠接收成功都以持久提交为前提。
- 新工作准入与既有流程恢复分开分配预算，补偿/结果回传/关闭所需工作有预留和公平调度，避免“队列满了所以永远无法补偿”的死锁。物理存储完全不可用时仍可能暂停恢复，必须告警，不能承诺无条件完成。
- 提供积压数量/年龄、重试、未知、死信、补偿进度与恢复耗时指标；日志不包含秘密数据。关闭时停止 claim，排空或交还工作，失联 worker 由租约回收。

### 8.8 Saga 完整契约与业务责任

使用版本化的显式状态机和普通 Kotlin 步骤函数。首版支持有界串行步骤、持久等待/期限、幂等命令、反向补偿与人工处置；不支持的并行 DAG、任意代码重放须明确拒绝，不用半套语义冒充支持。

- 启动先持久化 sagaId、流程版本与输入；返回“已接受”意味着流程可在进程退出后恢复，不要求请求协程一直存活。
- 发出步骤前原子记录执行意图、稳定幂等键和补偿责任。外部已成功而本地未记成功时，通过同键查询/重试确定结果，不能盲目开启下一步或补偿。
- 补偿使用自己的稳定操作键，必须容忍前向操作未发生、已发生、重复补偿；对尚在执行的前向操作，要有取消/确认或对账策略，不能“先补偿再被迟到执行重新生效”。
- 状态区分 RUNNING、WAITING、COMPENSATING、SUCCEEDED、COMPENSATED、NEEDS_ATTENTION 等概念；具体公共枚举待详细规范冻结。COMPENSATED 不代表数据库恢复到历史字节状态，更不代表退款等外部效果已经同步到账。
- 业务失败可触发补偿；调用方断连或取消等待不自动取消已持久接受的流程。业务取消是显式持久命令；流程超时也必须进入明确的停止、查证或补偿路径。
- Saga 不提供隔离。库存/余额等不变量由参与者的本地事务、约束、预留/确认/释放模型或版本检查保障；存在不可逆步骤时必须预先定义失败处置，不能承诺通用 undo。
- 同一部署可执行明确支持的多个流程版本；旧实例固定版本，缺失版本进入隔离告警。随机数、时钟与外部结果需落为步骤事实，不能恢复时重新计算改变已作出的决定。
- 每一步有输入/输出 schema、超时/重试、查询、补偿和人工处置契约。只提供 `try/catch` 与内存补偿列表不满足持久 Saga 验收。

**状态并发与未知结果：** 流程状态以版本 CAS 和 owner token 迁移，回传结果以 `(sagaId, stepId, 操作方向, invocationId)` 绑定；attemptId 只用于观测，不改变操作身份。回调与轮询可以竞争，但一次有效结果只推进一次；旧步骤、旧版本、伪造和互相矛盾的结果不得覆盖当前状态。NEEDS_ATTENTION 仍是待处置状态，不按已完成清理。

远端查询返回 NOT_FOUND 只有在协议能保证权威性和可见性时，才可作为未执行证据；最终一致查询、404、超时均不够。无法确定时保持 UNKNOWN，不触发可能与迟到动作冲突的补偿。补偿顺序按已知依赖反向推进：后一步尚未解决且前一步补偿会破坏业务安全时停止并人工介入，不无条件把剩余补偿全部执行完。永久无法访问外部系统时只保证状态可追踪，不保证业务自动收敛。

### 8.9 故障验收与完整交付门槛

测试使用真实 PostgreSQL、独立服务进程和可控故障代理；假时钟/假传输仅补充确定性窗口。按事务提交点注入故障，不用随机 sleep 作为唯一复现依据。

| ID | 故障注入 | 必须证明 |
|---|---|---|
| DC-01 | 业务与 Outbox 提交前/后杀进程 | 提交前均不生效；提交后事件可恢复，无成功业务对应的通知丢失 |
| DC-02 | 发送被接收后、本地记录确认前断网 | 允许重发；消费者本地业务效果不重复，确认层次正确 |
| DC-03 | 多消费者并发处理相同消息；消费提交后 ACK 丢失 | 唯一约束防重；业务与 Inbox 原子；每个订阅者独立处理 |
| DC-04 | 同键不同输入、不同租户、过期后重放 | 冲突拒绝、无跨租户结果泄漏、不过期后盲目执行 |
| DC-05 | claim 过期、旧 worker 恢复；续租与停机竞争 | 迟到提交被 fencing 拒绝；外部效果由幂等/查询保护，资源回收 |
| DC-06 | 库存/支付成功但响应丢失、Saga 状态尚未落库 | 结果可查证，不重复扣款，不跳过补偿责任 |
| DC-07 | 补偿失败、补偿结果丢失、补偿期间重启 | 同键恢复、无重复退款，耗尽后有人工处置状态与审计 |
| DC-08 | 前向动作迟到、取消和补偿交错 | 不出现补偿完成后重新扣款/占库存而无人追踪；未知结果进入对账 |
| DC-09 | 重复/乱序/缺口、毒消息、schema 不兼容 | 不破坏业务版本，隔离可见，其他不相关分区按策略继续 |
| DC-10 | 发布新流程/事件版本且旧流程未完成 | 固定旧语义执行或显式迁移；缺失处理器不误执行新版本 |
| DC-11 | 长时间断网、存储容量压力、大批到期、时钟偏移 | 队列/并发有界、退避无风暴、接收不虚假成功、恢复进度可测 |
| DC-12 | 重放窗口内清理、未完成流程归档、人工恢复越权 | 拒绝不安全清理/操作，不因丢失去重状态制造重复副作用 |
| DC-13 | 旧应用 outbox 与新模块迁移、回滚、双 worker 误启动 | 单一责任方，重复接管被阻止；保留稳定 ID 和待处理数据 |
| DC-14 | 持久 RECEIVED 后、业务处理前杀接收进程；重复投递 | 重启继续处理，RECEIVED 不误作 COMPLETED；载荷和结果回传均可恢复 |
| DC-15 | COMMIT 已生效但响应丢失；错误数据库/无事务调用桥 | 稳定键查询提交结果；错误会话调用被拒，无隐式双写 |
| DC-16 | 同一 Saga 结果回调、轮询、取消与过期 worker 并发 | 只有合法版本转换一次；矛盾/迟到结果可见但不错误推进 |
| DC-17 | 远端查询暂时 NOT_FOUND、幂等窗口过期、迟到成功 | 不盲目重试/补偿；未知进入对账；过期键不重新产生副作用 |
| DC-18 | 普通队列满时同时需要补偿与结果回传 | 恢复预留可用且有公平性；物理容量耗尽明确暂停并告警 |
| DC-19 | 载荷写入后落库失败、引用被提前删除、重复 ID 不同载荷 | 孤儿可回收；有效引用受保护；不执行篡改或不完整消息 |
| DC-20 | 嵌套事务返回后外层回滚 | 不提前发 durable ACK，不投递未提交事件 |
| DC-21 | 备份回退丢失已确认的状态 | 隔离发送并对账，不自动重放造成重复副作用 |
| DC-22 | 取消与最后一步成功并发 | 合法条件提交决定结果；迟到副作用不被丢弃 |
| DC-23 | RESULT 重复、回执丢失 | 不产生结果确认循环，消息重投不重复推进 |
| DC-24 | 本地 handler 写入后业务拒绝 | 业务修改先全部回滚，FAILED 独立持久化 |
| DC-25 | 换 messageId 重发同 invocation / startKey | 不重复业务动作或 Saga；内容变化拒绝 |
| DC-26 | 结果先于 ACK、续租与完成竞争、锁内跨租约期限 | 一次合法提交，无过期网络 worker 强写 |
| DC-27 | schema/旧表迁移中断或回滚、旧 worker 复活 | 无双执行、不丢身份；不兼容写入被阻止 |
| DC-28 | 清理与活动流程、payload 引用竞争 | 身份保护和有效载荷不提前删除，恢复依据完整 |

端到端场景最终校验订单、库存、支付账目之间的业务不变量，以及持久记录、计时器、连接和 worker 的释放；不能只断言返回 200 或最终有一条成功日志。输出每次故障的提交摘要、恢复轨迹、最终业务状态、重复次数与资源指标。

交付包括公共 API、存储/传输契约、一个真实数据库与一种真实跨服务传输、版本迁移、诊断/管理接口、容量策略、运维手册和上述故障套件。模块可以分步实现，但 N12-07 与 N12-10 及依赖验收未全部完成前，不标记“分布式一致性整套完成”，不以实验原型作为生产交付。

### 8.11 状态迁移契约

以下状态是语义标识，不是已发布 Kotlin 枚举。每个聚合有独立 version；所有变更按预期版本条件提交。worker 操作在获取提交所需行锁后检查 token 与租约；短本地事务取得有效锁后可持锁完成有界事务，期间租约自然到期不使已获锁的提交权失效，其他领取者必须等待/跳过锁行。未获得锁时已过期则拒绝。网络期间不得持锁，网络回来后必须重新校验；外部回调只携带操作身份，不接受其自称 owner。

#### A. 单一目的地的投递记录

| 原状态 | 条件/事件 | 新状态与原子效果 |
|---|---|---|
| 无 | 发布事务提交 | READY；稳定 messageId、目标与载荷摘要落库 |
| READY / RETRY_WAIT | 到期且获得 claim | LEASED；发新 token、attempt 序号、租约期限 |
| LEASED | 合法的持久接收回执 | HANDED_OFF；保存接收方及 receiptId，不表示业务成功 |
| LEASED | 超时/断连/可重试失败 | RETRY_WAIT；记录原因、下次时间；保持 messageId |
| LEASED | 租约到期并被重新领取 | LEASED；换 token；旧 worker 不能再写结果 |
| LEASED | 不可投递或重试耗尽 | QUARANTINED；保留消息与人工恢复入口 |
| QUARANTINED | 授权重放且原身份仍在有效窗口 | READY；追加审计，不替换 messageId |

HANDED_OFF 不再自动重发：接收方已承担持久恢复责任。接收方的处理失败通过业务结果/查询反馈；若未约定持久接收，不能使用此状态。QUARANTINED 不是“对端没有执行”，最后一次发送结果不明时必须保留该事实。首版不允许静默撤销已接受的投递；业务取消作为独立命令。

#### B. 接收记录与业务操作

| 原状态 | 条件/事件 | 新状态与原子效果 |
|---|---|---|
| 无 | 可信、有效的新消息 | RECEIVED；完整载荷或持久引用入库，之后才确认接收 |
| 任意已有状态 | 同身份且摘要相同 | 返回已有 receipt/status，不重复创建工作 |
| 任意已有状态 | 同身份但摘要不同 | 身份冲突；原记录不变，拒绝并审计 |
| RECEIVED / RETRY_WAIT | 到期并领取 | RUNNING；创建新 token 与期限 |
| RUNNING | 本地处理成功 | SUCCEEDED；业务写入、结果和结果 Outbox 同事务提交 |
| RUNNING | 可确认回滚的瞬态失败 | RETRY_WAIT；业务事务先回滚，再条件更新恢复状态 |
| RUNNING | 确定的业务拒绝且无未决副作用 | FAILED；保存拒绝结果并原子创建结果 Outbox |
| RUNNING | 外部副作用结果不明 | UNKNOWN；持久化查询/对账任务，禁止无保障重复执行 |
| RUNNING | 租约失效 | 本地纯事务模式可重领；外部模式进入 UNKNOWN 或按对端幂等协议重查 |
| UNKNOWN | 权威证据确认结果 | SUCCEEDED / FAILED；记录证据和结果 Outbox |
| UNKNOWN | 权威确认未执行且仍在安全窗口 | RETRY_WAIT；保持业务幂等键 |
| 非终态 | 预算耗尽/版本缺失/无法安全恢复 | NEEDS_ATTENTION；保留待处理责任和诊断 |
| NEEDS_ATTENTION | 授权恢复且版本/证据有效 | RETRY_WAIT 或 UNKNOWN；不能直接重置成新操作 |

旧文中 COMPLETED 是完成的统称，具体结果必须区分 SUCCEEDED/FAILED。SUCCEEDED/FAILED 的结果不可覆写；重复一致结果返回原记录，矛盾结果隔离。NEEDS_ATTENTION 不是可清理的成功终态；人工恢复必须提供证据、预期版本和恢复目标，不允许裸 `setStatus`。

本地模式失败后若恢复状态尚未来得及保存就崩溃，旧 RUNNING 的租约回收负责再次执行；业务事务回滚或已提交的终态决定是否允许执行，不能仅据 RUNNING 字样判断。对已接受的工作，取消 HTTP 等待者不撤销它；worker 取消同样不得提前 ACK 完成。

本地 handler 的确定业务拒绝必须先回滚本次全部业务写入，再在新的短恢复事务中以有效所有权保存 FAILED 与可选结果 Outbox；不能 catch 异常后在原业务事务提交部分修改。异常与取消保持现有数据库语义，只有明确的业务拒绝被分类为 FAILED；提交结果不明先查询原记录。失败记录尚未提交时崩溃允许重新执行已回滚的本地事务。需要“写入拒绝记录”等业务副作用时，必须另行建模为成功的领域动作，不偷换 FAILED 含义。

#### C. Saga 与步骤

| 原状态 | 条件/事件 | 新状态与原子效果 |
|---|---|---|
| 无 | 有效且幂等的启动请求 | RUNNING；固定流程版本、输入摘要和首步计划 |
| RUNNING | 启动后尚未计划首步就重启 | 扫描恢复同一流程，CAS 计划首步，不能创建第二流程 |
| RUNNING | 无在途步骤且取消意图有效 | COMPENSATING 或 COMPENSATED；没有补偿项时结束并记录取消原因 |
| RUNNING | 发出下一步 | WAITING；步骤 PREPARED、操作键、补偿责任和命令 Outbox 同事务提交 |
| WAITING | 当前步骤权威成功 | RUNNING 或 SUCCEEDED；步骤成功和下一步计划/最终结果同事务提交 |
| WAITING | 确定业务失败/可安全取消 | COMPENSATING；冻结前向计划，生成首个安全补偿意图 |
| WAITING | 期限到期且步骤结果未知 | WAITING（查询模式）或 NEEDS_ATTENTION；不得直接宣告失败并补偿 |
| COMPENSATING | 当前补偿权威成功 | 保持 COMPENSATING 并计划下一项，或 COMPENSATED |
| COMPENSATING | 补偿结果未知/可重试失败 | 保持并查证/重试；超预算进入 NEEDS_ATTENTION |
| NEEDS_ATTENTION | 授权且有证据的恢复 | 恢复到明确检查点；原子追加恢复命令与审计 |
| RUNNING / WAITING / COMPENSATING | 缺少处理版本、证据冲突或无法安全继续 | NEEDS_ATTENTION；保留原检查点及未决责任 |

SUCCEEDED、COMPENSATED 是不可改写的结束记录；结束后的新业务动作是新流程，不能篡改旧流程。COMPENSATED 仅在所有要求的补偿完成标准满足时成立；异步退款的“已受理”不能算“已退款”。串行流程同一时刻只能有一个可推进步骤，但查询/迟到回调仍可能并发，必须用 CAS 与步骤身份抵御竞争。

协调器步骤与参与者 Inbox 不是同一行状态：步骤为 PREPARED → AWAITING_RESULT（可选，收到接收回执后）→ SUCCEEDED/FAILED；结果先于接收回执到达时允许 PREPARED 直接转终态。PREPARED/AWAITING_RESULT 到期可转 UNKNOWN；UNKNOWN 只按权威结果结束，或在确认未执行时以同一 invocationId 回到 PREPARED。补偿拥有独立方向与 invocationId，不复用前向终态。步骤不暴露参与者 RUNNING/租约状态作为协调器事实。

对“取消”和“成功回调”的竞态，以同一持久状态的条件提交顺序决定：成功终态已提交则取消返回已结束；取消意图先提交则成功回调记录真实副作用并进入约定补偿路径，不能丢弃迟到成功。非法迁移返回冲突，不悄悄覆盖或自动重置。

### 8.12 存储原子操作与数据库桥

以下操作名仅用于描述契约，不预定方法签名。状态修改、审计以及待发送记录必须处于指定原子边界，不能拆成“写状态成功后再发事件”。

| 操作 | 必须在一个原子提交中完成 | 失败/竞争结果 |
|---|---|---|
| `appendInTransaction` | 当前业务事务写入 Outbox、固定目标/订阅版本与摘要 | 外层回滚一起消失；无有效同资源事务拒绝 |
| `accept` | 唯一性检查、载荷持久引用、RECEIVED、稳定 receiptId | 重复同摘要返回原 receipt；不同摘要冲突 |
| `claimBatch` | 有界领取、owner token、attempt、租约 | 并发 worker 不同时取得有效提交权；不保证外部执行只发生一次 |
| `renew / release / reschedule` | 校验 token、version、存储时间下的租约有效性并修改 | 失去所有权返回明确冲突；不复活旧 token |
| `completeLocal` | 校验并锁定当前所有权、执行本地业务、SUCCEEDED 结果、可选结果 Outbox | 任一失败整体回滚；拒绝结果按 B 表另事务持久化；不能调用远端 |
| `recordExternalResult` | 校验当前 invocation、证据、状态版本，保存结果和后续意图 | 重复结果幂等；矛盾/迟到结果进入核查，不覆盖 |
| `advanceSaga` | 消费结果去重、流程/步骤 version、下一动作/补偿与 Outbox | 竞争仅一个推进；另一方重读，不重复发新操作 |
| `manage / expire` | 授权操作的审计、CAS、期限/引用/去重保护检查 | 不允许越权重放、删除未结束状态或重置身份 |

数据库桥由 `neton-durable` 内部实现，通过 DbContext/DbSession 执行，不绕过现有拦截器。事务中禁止并行 SQL、嵌套 `REQUIRES_NEW` 假设和懒执行逃逸；依照现有数据库契约加入外层事务。`appendInTransaction` 返回只表示已参加事务，不表示外层已提交。需要向远端返回 durable ACK 的边界必须在外层提交确认之后，不能在嵌套事务返回时发送。

现有公开 DbSession 只有执行能力，不能单凭对象类型推断“正在事务内”。实施前须为数据库层评审最小资源身份/活动事务证明接口，或由明确的事务桥作用域传入不可伪造的证明；不得通过线程局部变量、SQL 猜测、自行开启第二个连接解决。该接口变更有独立兼容测试，不在本草案伪装成已有 API。

PostgreSQL 实现可用唯一约束、条件 UPDATE 和短行锁实现以上语义；具体 SQL 必须经过并发测试。READ COMMITTED 加条件锁不自动等于所有业务可串行化，业务跨行不变量仍需要约束/锁或适当隔离级别。`completeLocal` 在进入时验证未过期租约并持有记录锁到提交，阻止期间被重新 claim；事务有时限，不能在执行任意业务后仅作一次无锁 token 检查。

对提交结果未知，原操作身份查证成功前不重建任务；调用方取消不证明 COMMIT 未生效。存储仅在声明的 durability 配置下承诺恢复，必须记录同步提交/复制策略；落到内存缓存或异步复制节点丢失不能宣传成持久接收。备份回退可能丢失已经 ACK 的去重和流程状态，恢复后先隔离发送并对账，不允许直接全量重放。

存储能力表至少包含：原子批次、业务事务桥、唯一身份、版本 CAS、claim/存储时钟、持久扫描、载荷引用和终态保留。启动验证缺失能力，真实适配测试验证实现，不凭 Boolean 声明证明语义。一个存储实例独立保证这些能力，不假定不同数据库或实例之间有原子提交。

### 8.13 传输接收、业务结果与查询协议

协议级版本独立于业务 schemaVersion。公共信封包含协议版本、messageId、可信命名空间/租户、目标消费者、类型/schema、规范化摘要算法版本与摘要、operation/invocationId、causationId、有效期及载荷。载荷规范化规则固定；外部客户端可不计算内部摘要，由入口验证后生成。追踪字段不参与幂等身份。

| 协议结果 | 可以断言什么 | 发送方动作 |
|---|---|---|
| RECEIVED + receiptId | 接收方持久保存并承担恢复责任 | 标记 HANDED_OFF；需要业务结果时继续等待/查询 |
| SUCCEEDED / FAILED + receiptId + resultVersion | 对应操作的业务终态已持久提交，也证明接收成立 | 可同时记录 HANDED_OFF 与业务结果；校验来源、身份、摘要与版本，不能仅凭 HTTP 状态判断 |
| IN_PROGRESS | 已知操作尚未确定结果 | 按有界间隔查询，不重新启动业务 |
| UNKNOWN | 存在未决副作用或查询不能判定 | 保持未知，查询/对账，不盲目补偿 |
| REJECTED（未接受） | 经认证的本次请求未被持久接受 | 根据原因修正或重试；不证明历史同一操作从未执行 |
| ID_CONFLICT / EXPIRED / UNSUPPORTED | 身份内容冲突、有效期不符或协议/能力不支持 | 隔离并诊断；不能换键自动重发 |

首个参考传输选择现有 HTTP 客户端/服务端：入口认证后处理，202 仅搭配持久 RECEIVED 回执；200 可返回查询或已知终态，但必须解析协议体。409 用于身份冲突，410 用于已知过期，429/503 表示可重试压力；这些码本身都不证明之前未执行。网关 2xx、空响应、代理超时与连接断开均不是合法 durable ACK；无有效回执按发送结果未知处理。返回 retryAfter 也受本地期限和重试预算约束。

查询使用稳定 operationId/receiptId 和相同的授权范围；读取权威持久状态或明确标注非权威。NOT_FOUND 默认只表示查询未找到，不自动授权再次执行。若要返回可用于重试判断的“确认未接收”，必须证明权威读取、目标命名空间和历史保留边界，且仍按同键重发。无此能力的外部 API 进入 UNKNOWN/人工查证。

结果由接收方的结果 Outbox 发送至事先注册的可信目标，或由发送方查询；不能接受任意回调 URL 绕过 egress。回调也先经过持久 Inbox，再原子更新 Saga，因此回调已 ACK 但 Saga 尚未推进时可恢复。轮询与回调共用同一结果身份/version，重复不二次推进。有效回执到达时原发送 worker 已失去 lease，可由新处理者重新核验并 CAS 记录，旧 worker 不绕过 fencing 强写。

信封增加 `kind=EVENT|COMMAND|RESULT` 与受校验的 `replyMode=NONE|QUERY|CALLBACK`。只有请求结果的 COMMAND 可创建业务结果 Outbox；EVENT 默认只承诺可靠接收，RESULT 只返回持久接收回执，绝不自动产生“结果的结果”。QUERY 模式必须持久保存可查询结果但不必回调。相同 invocationId 的多个不同 messageId 仍关联同一个业务操作，不能通过更换消息 ID 绕过业务去重；业务身份同时绑定操作类型、方向和输入摘要。

确认匹配 namespace/tenant/source/target/messageId/invocationId/requestDigest/protocolVersion；认证在传输边界完成，不信任载荷自称来源。新接收前检查有效期；对已存在且摘要一致的消息，即使交付期限刚过，也允许在授权与结果保留期内查询已有 receipt，不能因超期使已交接责任变成不存在。有效期限制新接收，不取消已接受的执行责任；执行期限与去重保留期限独立配置。

未来 broker 适配需区分 broker 持久接收与终端消费者业务结果，明确重投、保留、ACK 与消费者恢复责任；不能把 broker ACK 翻译成 SUCCEEDED。兼容性测试覆盖协议版本、字段长度、未知字段与不支持 schema；已接受消息升级后仍需可读，未知业务版本进入隔离而不是丢弃。

### 8.14 新增契约验收与冻结条件

- 对 §8.11 每条合法迁移提供正例，对未列出的迁移提供拒绝样例；SUCCEEDED/FAILED 和流程终态不可覆盖。RECEIVED 与业务完成至少经历一次重启验证。
- 对 §8.12 每个原子操作，在提交前、提交后但响应前注入崩溃/取消；检查全有或全无以及稳定身份查询。并发 claim、租约续期、行锁等待与超时验证无失控提交。
- 对 §8.13 记录请求/回执摘要与持久轨迹：代理伪 2xx、丢回执、结果重复/矛盾、回调与查询竞态、过期键、越权 receipt 查询均有反例。
- 模块验收证明无独立 PostgreSQL 产物、只复用一个所选原生 driver；数据库后端禁用时没有额外池/扫描器，启用却缺能力时启动失败。
- 新增 DC-20：嵌套事务返回后外层回滚，不能发送 durable ACK 或可见事件；DC-21：备份回退丢失已确认状态时禁止自动发送并进入对账；DC-22：取消与最后一步成功并发，只有一个合法终态且迟到副作用可追踪。

这些用例与 §8.18 合并为一个发布门槛。当前只有规格，没有实现或通过记录；§8.15–8.17 给出 API、事务证明、schema 与迁移候选，须评审后才进入编码。不同模块分批开发不等于降低完整闭环的验收标准。

### 8.15 公共 API 候选（非现有可调用代码）

以下签名为设计记法，未创建 Kotlin 文件；所有类型归属和空值语义在实现前用编译样例核验。普通用户不接触 claim token、原始状态 UPDATE 或驱动。业务接口、运维接口、存储 SPI 分别授权/分级，不能把内部 store 注册给 Controller 任意调用。

| 所属接口 / 操作 | 输入 → 输出 | 语义与边界 |
|---|---|---|
| `DurableClient.submit`（suspend） | `Submission` → `SubmissionReceipt` | 独立持久提交成功才返回；有外层业务事务时拒绝，改用事务桥；异常/取消不证明未提交 |
| `DurableTransactions.enqueue`（suspend） | `TransactionProof, Submission` → `EnlistedMessage` | 加入同资源当前事务；返回待提交句柄，不能转成远端 ACK |
| `DurableClient.status`（suspend） | `OperationRef` → `OperationView` | 每次鉴权；返回状态、结果版本及查询权威性，不暴露内部可变对象 |
| `DurableClient.awaitResult`（suspend） | `OperationRef, WaitBudget` → `WaitResult` | 有界等待；超时返回未结束/未知观察，取消只终止等待 |
| `SagaClient.start`（suspend） | `SagaStart` → `SagaReceipt` | 稳定启动键、固定版本及摘要，重复返回同一 sagaId；不得嵌套于业务事务 |
| `SagaTransactions.start`（suspend） | `TransactionProof, SagaStart` → `EnlistedSaga` | 同资源原子启动；不同存储时必须从业务 Outbox 发送启动命令，不做双写 |
| `SagaClient.status / awaitResult`（suspend） | `SagaRef / WaitBudget` → `SagaView / WaitResult` | 与 durable 查询/等待同样的授权、取消及未知语义 |
| `SagaClient.cancel`（suspend） | `SagaRef, commandId, reason` → `CancelReceipt` | 持久取消意图，返回不等于补偿完成；同 commandId 幂等 |
| `DurableAdministration.recover`（suspend） | 目标、预期版本、命令 ID、证据、恢复动作 → `RecoveryReceipt` | 独立权限、CAS 与审计；仅允许白名单恢复动作，不提供 setStatus |

**值类型契约：** `Submission` 含稳定提交键、逻辑目的地、操作/schema 版本、kind/replyMode、载荷及三个独立期限（新接收、执行、去重保留）。调用方不能伪造可信租户/来源；由已认证上下文或明确的后台服务身份注入。`OperationRef` 含作用域和稳定 ID，持有它不等于有权限。`SubmissionReceipt` 表示本方已持久接受投递责任，不是远端 RECEIVED；`EnlistedMessage/EnlistedSaga` 不能提供 `awaitCommitted()`，避免在外层事务内等待自己提交的死锁。

`SagaStart` 的唯一键为 `(namespace, tenant, callerScope, flowName, startKey)`，流程版本和输入摘要绑定在该键上；重试时改变版本/内容返回冲突，不创建新流程。所有输入在第一次挂起前建立不可变快照或明确所有权转移，受单条大小与总预算限制。取消异常原样传播，持久接受结果未知时使用原提交键查询，文档明确禁止自动生成新键重试。

**处理器注册：** 启动期注册稳定 `HandlerId + schemaVersion`，freeze 后只读。`LocalHandler<I,O>` 在受控业务事务内执行，正常成功提交；明确拒绝/异常按 §8.11 回滚。`ExternalHandler<I,O>` 的 execute/query 接口在无业务事务环境执行，必须声明对端幂等窗口、权威查询能力和恢复策略。不能以“可查询”声称查询总能证明未执行。SagaDefinition 以稳定步骤 ID、方向、输入/输出 codec、补偿规则和期限注册；不持久化函数引用、KClass 名或捕获闭包作为流程身份。

**数据库新增契约：** database 层提供 `requireTransactionProof(resourceId)` 的候选能力，返回由它创建、不可序列化且不可由业务构造的证明；含资源、事务代次与活动状态，随外层提交/回滚失效。每次 enqueue 校验当前协程事务与证明匹配，不使用线程局部变量，不允许跨协程并行复用。现有 DbContext 继续拥有提交，durable 不能提前 commit。持久接收入口必须拥有顶层事务边界；存在调用方事务时拒绝，不伪装独立事务。COMMIT 中断后的 UNKNOWN 是观测结果，不能由“取消应回滚”的本地约定推断服务器已经回滚；该澄清须同步评审 database-session。

**SPI：** `DurableStore` 提供 §8.12 的语义操作，返回 `Applied(newVersion)`、`AlreadyApplied(snapshot)`、`Conflict(snapshot)`、`UnknownCommit(operationRef)`；不能将数据库异常一律翻译成 NotFound。`DurableTransport.deliver/query` 返回经过验证的协议结果或不确定传输结果，不直接改存储。原子批次限制在同一资源，不公开一个任意跨库 transaction(block) 冒充原子性。首版业务 API 走显式组件安装，不新增扫描式装配。

### 8.16 存储 schema 候选（PostgreSQL 首个验证方言）

这是逻辑 schema 与约束清单，不是可执行迁移 SQL。表名建议 `nd_*`；Saga 表只在安装 Saga 存储能力时由显式 migration 创建。已有应用业务表不改名，外键不跨数据库；每个本地资源可拥有自己的 durable 表。

公共字段：内部 ID 为 UUID，版本/计数为非负 bigint，时间为存储端 UTC timestamptz；namespace、tenant、来源、操作类型等限定最大长度且非空，无租户场景使用显式保留域而非 NULL 绕过唯一约束。状态用稳定文本值和 CHECK，不依赖 Kotlin 枚举 ordinal。载荷为有上限的 bytea 或持久引用二选一，摘要保存算法版本与固定长度值。敏感字段不放未脱敏 JSON 日志。

| 表 | 关键字段与唯一性 | 原子约束/主要索引 |
|---|---|---|
| `nd_submission` | 作用域、submissionKey、摘要、operationId、目的地快照、retentionUntil | UNIQUE(作用域, submissionKey)；与 Outbox 同事务插入；保留稳定提交查询 |
| `nd_outbox` | messageId、固定 targetId、operationId、kind、replyMode、载荷、状态、attempt、nextAt、version、ownerToken、leaseUntil、receipt | UNIQUE(来源作用域, messageId, targetId)；READY/RETRY_WAIT 到期部分索引、LEASED 过期索引；扇出每目标独立行 |
| `nd_inbox` | 来源/租户/consumerId/messageId、摘要、receiptId、operationId、receivedAt | 消息键唯一；receiptId 唯一；提交接收不等于完成，处理状态从 operation 读取 |
| `nd_operation` | 作用域、操作类型/方向、invocationKey、请求摘要、模式、本地/外部处理器版本、状态、结果/version、lease、nextAt | UNIQUE(作用域, 操作类型, 方向, invocationKey)；Inbox 与 operation 原子创建/关联；同 invocation 多消息仍仅一次本地效果 |
| `nd_saga` | 作用域/startKey、flowName/version、输入摘要、状态、currentStep、cancelRequested、version、nextAt、lease | 启动键唯一且不含 flowVersion；活动流程/到期扫描索引；取消意图独立字段 |
| `nd_saga_step` | sagaId、stepId、方向、invocationId、输入/结果、状态、version、补偿责任 | UNIQUE(sagaId, stepId, 方向)；invocationId 唯一；串行执行权由 saga version 决定 |
| `nd_timer` | ownerType/id、timerKind、generation、dueAt、状态、lease | UNIQUE(ownerType, ownerId, timerKind, generation)；与计划步骤/状态同事务；触发消费和后续计划原子化 |
| `nd_identity_guard` | 作用域、键类别、键或关闭代次、摘要/终态引用、拒绝边界 | 墓碑/已关闭代次防历史重放；压缩结果不删除仍有效的身份保护 |
| `nd_audit` | commandId、目标、前后 version、主体、证据引用、动作、时间 | 管理命令唯一；审计与状态变更同事务；追加写，不以日志替代 |
| `nd_payload_ref` | 对象引用、摘要、大小、状态、最短保留期限 | 引用关联表跟踪有效 owner；GC 先原子标记可回收，再删对象，幂等恢复 |
| `nd_control` | 存储 schemaVersion、读写兼容范围、部署/迁移 epoch、停写/停 claim 标志 | 每资源唯一；worker 写入校验 epoch，防旧版本继续接管 |

inbox 是接收身份，operation 是业务状态；两者不能各自存一份可独立更新的业务终态。operation 与 result Outbox、Saga 消费结果与下一命令各在同一事务。回调接收记录与对应 Saga 必须在同一个协调器资源提交，不能通过两个数据库表模拟原子推进。

ownerToken 与 leaseUntil 同时为空或同时存在；仅有执行权的状态允许存在有效租约。成功/失败结果固定 resultVersion，不可修改；传输重投保持消息与操作身份。到期扫描采用有界批次与行锁/条件更新，锁等待有期限。租约续期也增加记录版本，worker 必须刷新预期版本，不可因续期使自己的完成更新无条件覆盖竞争者。

统一锁顺序：管理/流程根记录 → operation/step → 待消费 inbox → 新 outbox/timer/audit；领取事务不跨网络、不长时间持有多个聚合。批量按稳定 ID 排序；死锁可回滚重试纯存储事务，不能自动重跑已经发生外部效果的整个 handler。业务自己的锁仍需遵守数据库约束并接受死锁回滚测试。

索引/唯一键的作用域在类型定义、DDL 和查询中必须一致，不能只依赖调用者过滤 tenant。不存在主键碰撞、CHECK 或唯一冲突时的静默 upsert 覆盖请求摘要。迁移历史复用现有 migration 机制，不另建自动升级服务；保留窗口、结果查询窗口与载荷 GC 的外键/引用约束一起测试。

### 8.17 版本升级、旧事件桥与回滚

**新 schema 升级：** 显式 CLI migration，单一迁移锁、版本和 checksum；先 expand（新增兼容表/列/索引）→ 新旧兼容读写验证 → 分批 backfill（游标、幂等、校验）→ 切换写入版本 → 确认旧 worker 退出后 contract。运行期启动只校验兼容范围，不修改生产 schema。非事务 DDL 步骤必须有可恢复检查点，失败不得伪记成功。

**回滚边界：** 数据库扩展兼容时可回滚二进制；已经写入旧版本不理解的状态/schema 后，禁止直接回退旧 worker，先暂停接收/claim 并运行经过验证的数据转换或前向修复。终态、幂等键和已确认 receipt 不能通过 down migration 删除。备份还原属于灾难恢复，提升恢复 epoch 并隔离发送、对账后解封，不把数据回退当普通发布回滚。

**旧 event v1：首版默认共存，不原地接管。** 老的 RETRYABLE 继续由原投递器处理旧表；新集成事件通过显式桥写新 Outbox。桥从稳定旧事件身份/监听者身份派生唯一映射，发布时选择一条路，不能旧 listener 和新 subscriber 同时执行同一业务副作用。只有未来跨进程选定事件才外发，旧 SYNC/BEST_EFFORT 不变。

如需搬迁历史积压，执行以下独立、可中断的运维流程：

1. 验证事件类型/schema、消费者、租户与幂等键映射；无法唯一映射的行隔离，不能生成随机新 ID。
2. 暂停对应发布与旧 claim，等待旧 worker 和外部在途动作排空/查证。旧实现不认识新 epoch 时必须停止并撤销其写入/发送能力，单写新控制表不足以 fence 旧进程。
3. 在停写屏障内复制稳定 ID、状态、attempt、期限、载荷和消费身份，记录唯一 old→new 映射与批次校验。相同数据库可事务复制；跨库用可恢复复制日志，确认目标完成前不删源。
4. UNKNOWN、旧版本缺失或对端幂等窗口已过的记录保持隔离；新记录仍禁用 claim。核对行数、摘要、消息/业务身份和账目，再切换唯一发布/消费所有权。
5. 观察恢复后逐步放量。新 worker 已执行外部动作后不得简单重开旧 worker；回滚必须同步已执行事实并重新排空/对账，不能仅切配置。
6. 保留旧表只读和映射至重放/审计期限结束，再显式清理。不同版本的长期并存须公布兼容矩阵，禁止无限期双写。

schemaVersion、协议版本、事件 schemaVersion、流程版本和部署 epoch 是不同维度，不用一个框架版本号替代。已接受工作在升级后仍能找到固定 handler/codec；移除版本前必须证明无活跃引用，或将对应工作隔离并给出迁移方案。

### 8.18 r5 交叉评审与补充验收

| 级别 | r5 矛盾/遗漏 | r6 处理 |
|---|---|---|
| P1 | 所有结果都产生结果 Outbox，可能形成无限确认循环 | RESULT 只做持久接收确认，COMMAND 的 replyMode 控制业务结果 |
| P1 | handler 业务拒绝未规定先回滚，可能提交部分业务写入 | 拒绝先回滚，再短事务存 FAILED；COMMIT 未知先查证 |
| P1 | 未过期 token 要求与持锁事务跨期限冲突 | 获取锁时校验；持锁有界事务独占，网络返回后重新校验 |
| P1 | messageId 防重不等于业务 invocation 防重；启动超时可能重复建 Saga | 消息、操作、启动三层唯一键与摘要绑定 |
| P1 | 协调器 PREPARED 套用参与者表，且结果先到无法推进 | 独立步骤状态；终态含 receipt，可先于接收回执推进 |
| P1 | 旧 worker 不识别新 fencing，复制历史后可能双执行 | 默认共存；搬迁必须停写、排空、唯一映射和所有权切换 |

新增 DC-23：RESULT 重复/丢回执不产生结果循环；DC-24：本地 handler 写入后拒绝，业务修改全部回滚；DC-25：换 messageId 保持同 invocation/startKey，不重复动作/流程；DC-26：结果先于 ACK、完成与续租竞争、锁内跨期限，仅一次合法推进；DC-27：迁移中断/回滚、旧 worker 复活和不兼容状态写入被阻止；DC-28：清理身份保护、payload 引用与活动流程竞争，不丢恢复依据。

公共 API 验收还包括：Kotlin/Native 编译样例、取消语义、不可伪造/过期事务证明、嵌套事务待提交句柄不可当 ACK，以及零业务 DB 的外部 API 编排。schema 验收必须运行真实 DDL、唯一约束、CHECK、并发锁顺序和 expand/contract 测试；文档构建不能证明这些用例已通过。全部 DC-01–28 与 API/schema/协议测试是整套交付条件。

## 9. CQRS：按需分离，不强制事件溯源（P1）

- 最小形式是命令函数负责写入、查询函数返回 DTO，可共用一个数据库。无需先引入 CommandBus、Mediator 或新注解。
- 只有独立读模型有实际价值时才异步投影；写侧授权、约束、事务仍在业务层。
- 投影去重、更新和 checkpoint 原子提交；处理重复、乱序、缺口、版本不兼容与重建。重建使用隔离版本并明确切换，不能把半成品读模型直接上线。
- 查询暴露可理解的新鲜度/版本；“写后立即读”通过版本等待、读写侧回退或明确最终一致性策略解决，不默认读取陈旧数据还声称成功同步。
- 事件溯源、全历史重放和复杂通用工作流不是 CQRS 的前提，不纳入默认 1.2.0 范围。

## 10. 统一网关是不是核心？

**结论：统一入口可以是部署架构的重要组件，但不应是 Neton core 的强制依赖，也不应成为所有内部调用的唯一通道。**

| 部署需求 | 默认选择 | Neton 的职责 |
|---|---|---|
| 单应用或模块化单体 | 现有 HTTP 入口，可配外部反代 | 不增加额外网络跳转 |
| 多系统统一域名、TLS、路由、入口限流 | 已有网关/Ingress 优先 | 身份信任、trace、健康、drain 契约对接 |
| 应用专用聚合/BFF | 独立应用，复用可靠客户端 | 聚合逻辑与领域授权留在应用 |
| 必须自定义协议或深度代理策略 | 独立可选 Neton gateway 实验 | 先证实既有代理无法满足需求，再投入 |
| 服务间大量内部调用 | 服务发现直连或 mesh | 不要求全部绕行北向网关 |

Spring Cloud Gateway 本身是独立网关项目；Axum 复用 Tower 中间件，而 Pingora 面向代理服务，Linkerd 将代理数据面与控制面分开。这些说明“应用框架 + 独立流量基础设施”是可行的组合，不证明 Neton 必须自研三套系统，也不能把它们的生产吞吐当作 Neton 的性能证据。参考见 §15。

如果未来实现网关，必须独立验收：流式转发背压、逐跳头处理、请求边界、大小上限、目标地址校验、TLS 校验、连接池、WebSocket 长连接退出、路由快照原子更新与回滚。网关鉴权不能代替下游领域授权；客户端伪造身份/forwarded 头必须在信任边界处理。

AI gateway 的模型路由、计费和协议转换是业务产品，不等于通用 HTTP 网关；两者只复用客户端、诊断和出站策略，不互相绑入核心。

### 11.2 编译期架构检查：参考 Encore.ts

**参考依据：** [Encore 应用结构](https://encore.dev/docs/app-structure)与 [Encore.ts](https://encore.dev/docs/ts)将服务和资源声明组成应用模型，用于开发工具与服务关系展示。

**借鉴设计：** 复用现有模块、路由、权限、Job、事件声明，生成一个版本化 ApplicationManifest，供依赖检查、契约生成、架构图和诊断定位共同使用。区分声明依赖、静态分析发现的引用和运行期实际调用，不把架构图解释成穷尽所有动态路径的证明。

**不照搬：** 不绑定 Encore 云平台、基础设施自动创建或远程调用透明化；不要求重写现有 Controller，也不新增一套平行的资源声明 DSL。

**实现边界：** KSP 负责可见声明及其元数据，应用聚合检查跨模块装配；Gradle 可见性与静态规则检查依赖边界。运行期配置选择仍在启动时校验。生成器只能写构建输出，不改业务源文件，不在运行期重新扫描生成。

**验收标准：**

- 相同输入在 clean build 与增量构建中生成相同规范化清单；跨工作目录不因绝对路径或时间戳产生无意义差异。
- 重复路由、循环模块依赖、未声明的受检依赖、缺失能力各有编译失败样例，错误含稳定规则码及源码位置；明确列出不在静态检查覆盖范围内的路径。
- 修改一个模块后相关生成物正确失效，不残留已删除入口；不相关模块无语义变化。
- 架构图、API 导出和诊断条目能关联同一构建及清单摘要，清单无密钥和运行期身份信息。

### 11.3 契约生成：参考 Swift OpenAPI Generator

**参考依据：** [Swift OpenAPI Generator](https://github.com/apple/swift-openapi-generator)从 OpenAPI 生成客户端和服务端代码，生成接口与传输实现分离；[Hono RPC](https://hono.dev/docs/guides/rpc)与 [Elysia](https://elysiajs.com/blog/elysia-14)作为类型与请求契约联动的辅助参考。

**借鉴设计：** 统一契约模型，接口、编解码和网络传输分离。自有 API 以 Kotlin 路由/DTO/序列化声明为权威来源；外部 API 可以以 OpenAPI 为权威来源导入客户端。每个 API 必须选定一个来源，生成物只读，不做含糊的双向同步。

**不照搬：** 不强制手写 YAML，不靠 TypeScript 类型体操增加 Kotlin DSL，不把类型推导当运行期校验。ts-rest 仅保留历史设计参考：其[官网](https://ts-rest.com/contract/overview)在本次核对时声明不再维护，不作为持续跟踪主基线。

**实现边界：** 生成在构建期完成，客户端依赖传输契约而非具体引擎。导入器与导出器公布支持的 OpenAPI/schema 子集；未知构造、自定义 serializer 无法准确映射时明确失败或要求显式声明。HTTP、WebSocket、RPC 各自保持协议契约，不强塞进 OpenAPI。

**验收标准：**

- 生成客户端和服务端样例必须真实编译并完成网络往返；至少覆盖可空/缺失/默认值、枚举、日期与数字范围、错误响应及已声明支持的多态。
- serializer 输出、运行期验证和导出 schema 使用同组正反例对照；字段转换前后的类型不能混淆。
- 契约差异按请求与响应方向检查兼容性；新增必填请求字段、移除响应字段等反例能被识别，不声称覆盖所有语义兼容问题。
- 更换受支持传输实现不重写业务 DTO；不支持的流式或编码能力在构建/装配时拒绝，不能静默缓存全量内容降级。

### 11.4 可追溯诊断：参考 Rust 与 Swift 的分层

**参考依据：** [Rust tracing](https://docs.rs/tracing/latest/tracing/)提供 span、event 和 subscriber；[Swift Service Context](https://github.com/apple/swift-service-context)提供类型安全的上下文容器，[Swift Distributed Tracing](https://github.com/apple/swift-distributed-tracing)提供追踪接口。

**借鉴设计：** 类型化上下文、结构化事件、带起止的 span，以及可替换观察/导出后端。一次 operation 与多次 attempt 分开，连接、TLS、数据库与事件投递能够关联源码和构建信息；复用 §5 的阶段定义。

**不照搬：** 不依赖线程局部变量跨挂起点维持关联，不复制 Rust RAII guard 的使用方式，不硬依赖某个遥测平台；不允许追踪上下文被当成授权凭据。

**实现边界：** 复用既有日志和路由观察链，通过协程上下文传递最小关联信息；跨网络传播字段有白名单、长度上限和信任规则。遥测元数据与请求身份分离，不能把可变 HttpContext 留给长生命周期任务。导出器拥有自己的有界队列、关闭期限与失败计数。

**验收标准：**

- 并发请求、跨 dispatcher、子协程取消及后台任务交接的确定性测试证明上下文不串线；operation/attempt 父子关系与结束次数正确。
- 超时、重试、网络断连的诊断可区分逻辑失败与尝试失败；观察器失败不改变业务结果或吞掉取消。
- 导出阻塞、队列满、停机和禁用模式均有测试；测量禁用及启用两种模式的分配、吞吐和尾延迟，阈值按 §13 预先固定。
- 敏感字段用自动化样例证明不泄漏；恶意传播头不能无限增加内存、标签基数或强制全量采样。

### 11.5 服务发现：参考 Swift Service Discovery

**参考依据：** [Swift Service Discovery](https://github.com/apple/swift-service-discovery)及[官方设计介绍](https://www.swift.org/blog/swift-service-discovery/)将服务身份、实例和发现后端分离。参考其接口职责，不照抄特定版本的回调形态。

**借鉴设计：** 逻辑服务身份解析为实例集合，后端可以更换；Neton 采用 §7.1 的不可变快照与生命周期约束。发现只描述候选实例，实例选择、连接池、注册租约和请求重试分别有明确所有者。

**不照搬：** 不自研注册中心，不默认注册所有应用，不以“接口统一”掩盖 DNS 与注册中心不同的 TTL、订阅和一致性能力。发现成功不代表节点健康或服务身份可信。

**实现边界：** 首批静态配置与 DNS，不强迫部署 mesh。后端无源版本时可用本地刷新代次抑制迟到结果，但不能把它宣传成注册中心全局版本；TTL 不可得时使用显式配置的有界缓存期。订阅必须支持取消和退出，快照刷新不进入逐请求热路径。

**验收标准：**

- 同一套后端契约测试覆盖首次无实例、显式空集合、刷新失败、快照过期和恢复；区分“节点被摘除”与“暂时无法刷新”，不能错误复活被撤销的地址。
- 用可控时序制造旧刷新晚于新刷新完成、订阅取消时回调到达，证明不覆盖新快照且不泄漏 watcher。
- 节点退役不再接收新分配，已有请求按时限排空；真实 DNS/网络测试验证地址变化、TLS 服务身份和 egress 校验。
- 多连接同时刷新只有受限的后端请求；记录快照年龄和来源但不暴露注册凭证；停止后无续租/刷新任务残留。

### 11.6 可靠调用：参考 Tower 的组合与背压

**参考依据：** [Tower](https://docs.rs/tower/latest/tower/)将 Service/Layer 契约与超时、限流、均衡等实现分离，配有 tower-test；[ServiceBuilder](https://docs.rs/tower/latest/tower/struct.ServiceBuilder.html)明确组合顺序影响在途数量等语义。

**借鉴设计：** 调用策略可组合，准入与实际调用分开建模；稳定的小契约配可控测试工具。借鉴 Tower 的 readiness/背压目的，在 Kotlin 中表达为可取消的准入/许可，不机械复制 `poll_ready`。

**不照搬：** 不将层层嵌套 Rust 泛型暴露给业务，不重建现有入站 around 链，不把任意请求都视为可克隆可重试，也不把框架层的 suspend 函数包装成“远程调用无失败”的本地函数假象。

**实现边界：** §6 的总期限在最外层；排队、发现、连接和退避均消耗预算。分别标明限制逻辑操作数或实际 attempt 数，退避不占网络 attempt 许可但仍受有界 operation 准入约束。取消释放许可；流式调用的资源占用延续至响应体结束/关闭，不能拿到响应头就释放连接或全部容量。

策略在启动时形成可检查的执行顺序，错误配置明确拒绝。鉴权与 egress 不能因重试换节点而绕过；可重试失败不等于整个逻辑操作失败，熔断统计单位要显式说明。共用的调用策略不抹平 HTTP 与 msgtrans 的流式、提交和取消差异。

**验收标准：**

- 假时钟与可控传输测试精确验证总期限、单次期限、退避和取消；总预算到期不再发新 attempt，取消后没有隐藏重试。
- 策略顺序测试证明排队/在途计数符合声明；并发压力下限额不越界，所有失败出口许可归零，慢流式响应也受限制。
- 无幂等保障的有副作用请求、不可重放请求体、已经向调用方交付的流式响应均不能透明重试；响应丢失场景如实暴露未知结果。
- 使用两个以上真实服务实例验证摘除、慢节点与恢复；记录实际上游尝试次数，证明客户端/网关重试不会超出配置的链路预算。
- 分别验收无策略快路径、开启策略、过载与故障恢复，既看吞吐也看错误、p99、公平性和资源上限，不用微基准替代生产调用路径。

## 13. 稳定性、性能与验收

- 每个 SPI 配一致性套件；假实现验证可控竞态，真实网络/数据库验证实际副作用，两者不可互相替代。
- 故障矩阵覆盖断连、延迟、重复、乱序、进程被杀、节点摘除、租约过期、时钟偏移、滚动版本与恢复后的积压。
- 记录连接、Job、计时器、缓冲、队列、持久记录的创建与释放；长稳测试看资源是否持续增长，不能只看最后请求成功。
- 空闲、大吞吐、慢消费者、下游故障分别测试；关闭可选模块后不得启动其后台任务或引入其重试行为。
- Kotlin/Native release 构建记录编译器、依赖、提交、二进制摘要、CPU 拓扑、cpuset/quota、worker 数、GC 配置。Kotlin 升级单独 A/B，不和架构重写混成一个变量。
- 负载发生器与服务端隔离；同机同负载交替对照，记录实际请求数、错误、超时、CPU/request、RSS、分配和 p99。诊断构建的分配统计不能直接代替 release 吞吐结论。
- 噪声与失败轮保留，预先规定作废规则；`rps/CPU%` 不免疫环境干扰。不承诺追平特定榜首，改动要有生产路径上的证据。
- 每项实施前冻结容量、时延和允许回退阈值及测量方法。首次建立基线后再定数值，禁止拿到结果后放宽门槛宣布成功。

## 14. 兼容性与不做事项

1.2.0 优先增量兼容，现有 HTTP/WebSocket 应用不必启用发现、CQRS、Saga 或网关。破坏性变更不能只靠改草案合法化，必须有迁移方案与版本策略评审。

新事件和持久化状态需要前后版本混跑验证；新增稳定 API 先通过契约套件，实验 API 明确标识。文档、配置 schema、诊断字段与实现一起交付。

当前不做：自研注册中心、通用配置中心、全套 Service Mesh、通用 XA/2PC 协调器、强制事件溯源、无限动态脚本、默认请求内容录制、用于宣传的跨语言性能保证。分布式鉴权、凭证轮换与 mTLS 的集成边界必须定义，但不自建 CA/身份平台。

待评审决策：阶段 A 的发布范围；首个注册中心与跨服务传输；§8.3 模块命名及对 event v1 的边界修订；性能验收硬件与阈值。Saga 开发期间可以实验验证，但整套交付必须通过完整门槛。本文给出候选设计，不授权发布或创建新模块。
