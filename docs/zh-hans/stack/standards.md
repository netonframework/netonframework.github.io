# netonstream 技术栈工程标准

> 状态：草案 v0（2026-10-10）。适用于 `com.netonstream` 下的基础库：io、http、websocket、quic、http3、tls（含 tls-http、tls-websocket）、
> msgtrans（含 msgtrans-quic、msgtrans-websocket）。openssl（openssl-kotlin）由其维护者另行负责，本标准只约束本栈对它的使用方式。
>
> 目标：**证据可追溯、行为可验证、版本可升级**。一次测试全绿、功能数量都不能替代这三点。

## 1. 原则

1. **标准是 RFC，不是参考实现。** 各库首版复刻参考实现（hyper、quinn、tungstenite、h3、msgtrans-rust 等），参考实现自身的偏差同样需要识别；
   与参考实现不同的地方（各库 SPEC 中的 ⚖️）与与 RFC 不同的地方分开记录。
2. **声明支持什么，就为它提供证据；没声明的不承诺。** 能力范围由支持声明（§2）界定，未列出的视为不支持。
3. **证据必须可复核。** 每条证据给出测试名、脚本或运行记录，以及对应的版本与日期；"判定通过"与"行为已验证"分开标注（§3）。
4. **失败不能被重跑抹掉。** 首次失败的记录是证据的一部分（§6）。
5. **运行时契约与协议一致性同等重要**（§7）：生命周期、取消、背压、资源上限与跨层组合出错时，一样是缺陷。

## 2. 支持声明（每个库必须有）

每个库维护一份支持声明，放在本目录 `libraries/<库>.md`，内容：

| 项 | 要求 |
|---|---|
| 规范与版本 | 每个 RFC / 草案的编号与版本；只实现部分时写明哪一部分 |
| 角色 | 客户端、服务端、两者；中间件 / 代理语义另列 |
| 扩展 | 支持的扩展（如 RFC 9221 数据报、permessage-deflate），各自默认开关 |
| 明确不支持 | 列出并给理由；"参考实现也没有"是事实，不是理由，需说明为何当前不做 |
| 偏离 | 与 RFC 的偏离（如更严格的默认值）、与参考实现的偏离（引用 SPEC 的 ⚖️ 条目） |
| 平台 | 在哪些目标与驱动上**运行过**测试，哪些只**编译过** |
| 资源上限 | 默认上限与可配置项（见 §7.2） |
| 参考实现 | 名称、版本、提交号（复刻时所依据的） |

支持范围的变更（新增能力、改为不支持）是兼容性事件，按 §8 处理。

## 3. 证据分级

| 级别 | 含义 | 可接受的依据 |
|---|---|---|
| **V** 已验证 | 测试直接断言了该行为 | 单元 / 集成 / 模拟测试，断言具体的字节、状态、错误码或时序 |
| **I** 互通观察 | 与独立实现互通时观察到该行为 | 互通脚本的日志或断言（对端名称与版本必须写明） |
| **S** 套件判定 | 外部套件判定通过，但行为本身未被独立确认 | 套件名、版本、命令、运行记录；套件提示"跳过 / 不可能"的用例不得记为 S |
| **A** 分析 | 代码审查或推理得出，未经测试 | 审查记录（谁、何时、看了什么）；只用于难以自动测试的条款，并说明原因 |
| **G** 缺口 | 声明支持但没有证据 | 必须出现在路线图（[roadmap](./roadmap.md)）中 |
| **N** 不适用 / 不支持 | 支持声明之外 | 引用支持声明中的理由 |
| **M** 测量 | 性能或资源的测量结果，不证明正确性 | 场景、硬件与核数、驱动、负载工具与版本、轮数与分布、宿主负载；见 §9 |

规则：
- 一项能力可以有多条证据，取最强的一条定级，但其余也列出（互通与单元测试互相补充）。
- **S 不能单独支撑"符合某 RFC"的结论**：外部套件只覆盖它声明针对的版本与用例。例如 h2spec 声明针对 RFC 7540 / 7541，RFC 9113 的变化需另行覆盖；
  h3spec 的 `CRYPTO in 0-RTT` 在对端不做 0-RTT 时提示跳过却判通过（http3 SPEC 的验收记录），这类结果只能记为 G。
- 证据随代码变化：被测代码改动后，相应证据需重跑；无法重跑的标注"基于版本 X"。

## 4. 条款清单

- 按支持声明中的**版本、角色与扩展**，从 RFC 中提取规范性条款：MUST、MUST NOT、SHOULD、SHOULD NOT，以及有条件的要求（"如果……则 MUST"）。
- 每条给出：条款位置（RFC 节号）、适用角色、证据（§3 级别 + 依据）、备注（偏离、不适用的原因）。
- 先做**高风险条款**，再逐步补全：
  1. 解析与边界：长度、整数溢出、未知类型、重复字段、非法组合；
  2. 状态机：非法状态下收到的帧 / 消息、关闭与重置的各种交错；
  3. 资源：流数、窗口、缓冲、解压输出、握手与连接数；
  4. 安全相关：认证、证书、重放（0-RTT）、放大攻击、请求走私。
- SHOULD 不遵循时写明理由；不能自动测试的条款允许以 A 级证据收尾，但要说明为何不能测试。

## 5. 外部一致性套件与互通

| 库 | 套件 / 互通 | 当前记录 |
|---|---|---|
| http | h2spec 2.1.1（RFC 7540/7541）；curl 互通（HTTP/1.x、h2c） | h2spec 145/145 |
| http3 | h3spec 0.1.13；h3 / h3-quinn、aioquic 互通 | h3spec 49/49（其中 0-RTT 一项实际未检验） |
| websocket | Autobahn\|Testsuite，客户端与服务端两个方向 | 各 517 用例无失败 |
| quic | QUIC Interop Runner（本库、quinn、quic-go、ngtcp2 双向）；quinn-peer 互通 | 见 [quic](./libraries/quic.md) |
| msgtrans | msgtrans-rust 2.0.0-beta.2 互通（TCP、QUIC、WebSocket） | CI 中 QUIC 与 WebSocket 双向通过 |

规则：
- **适用用例不得有未解释的失败。** 不适用、套件自身缺陷、标准变更导致的不一致，都要有可审计的记录（文件、日期、版本、理由），不得静默跳过。
- 套件的版本与命令固定，写在库的支持声明里；升级套件版本当作一次新的验收。
- 只在单个组合上跑过的结果不外推到其他组合（例如只在 Linux epoll 上的互通）。

## 6. 失败的处理

1. **首次失败即保存**：种子、日志、抓包或密钥日志（如有）、版本、平台与驱动、CI 运行链接。
2. **重跑成功不能抹掉首次失败**：失败记录保留，直到找到原因并以回归测试锁定，或明确归因为基础设施问题（并写明证据）。
3. **区分基础设施故障与产品缺陷**：宿主负载、网络、runner 资源造成的失败要有依据（例如负载记录），不能凭推测归类。
4. **时过时不过的失败视为缺陷**，进入路线图（例：QUIC Interop Runner 的 handshakeloss / handshakecorruption 在不同轮次时过时不过，原因未明）。
5. 未解释的失败阻断发版，例外按 §11 处理。

## 7. 运行时契约

自实现 I/O 与协议栈的库，运行时契约与 RFC 一致性同等优先。每个库在支持声明中列出契约，并给出测试（契约测试应当在删去对应实现后失败）。

### 7.1 生命周期与并发
- 缓冲的所有权与有效期：挂起期间借出的内存、零拷贝切片、借用的缓冲（如 neton-io `Buffer` 的 SHARED / BORROWED）。
- 取消：取消与完成的竞争；取消后读写的精确计数（io-testkit 的 `IoStream` 一致性套件，例："被取消的写入恰好推进已发送的字节"）。
- 关闭：关闭后不再回调；幂等；半关闭；关闭后的 fd 复用。
- 线程：对象属于哪个反应器线程，跨线程调用的投递规则。

### 7.2 资源有界
- 每连接与全局的内存上限：读写缓冲、待发送队列、重组缓冲。
- 数量上限：流、握手中的连接、未接受的连接、定时器。
- 放大与解压：解压输出上限、防放大限制。
- 时间上限：握手、空闲、请求、关闭握手的超时；调度预算（每轮的工作上限）。
- 每个上限给出默认值、配置项与"超限时的行为"（拒绝、关闭、背压），并有测试。

### 7.3 组合正确性
单库全绿不能替代组合测试。需要覆盖的组合（至少）：
- HTTP/3 → QUIC → TLS 接口 → UDP → 反应器：取消、背压、关闭与错误传播；
- HTTPS / wss → tls → TCP → 反应器（含 Windows IOCP，已发现过取消写入计数的缺陷）；
- msgtrans 会话 → 各传输（TCP、QUIC、WebSocket）。

### 7.4 持续运行
- 慢客户端、连接抖动、丢包 / 乱序 / 复制（已有：quic 的 `LossyRelay` 与协议层损伤模型）；
- 资源耗尽（fd、内存）下的行为；
- 长时间运行后的内存、句柄与定时器数量不增长。

### 7.5 模糊测试
- 确定性种子的模糊测试（已有，便于复现）与**覆盖率引导**的模糊测试互补；后者发现的输入沉淀为确定性回归用例。
- 每个面向对端字节的解析器都要有模糊目标。

## 8. 兼容性

每次发版检查四项，任何一项的不兼容都按"破坏性变更"处理：

| 维度 | 检查方式 |
|---|---|
| 源码 | 公开 API 的签名与可见性 |
| 二进制 | klib ABI 快照（Kotlin Gradle 插件的 ABI 校验）；含 cinterop 的库单独核对 |
| 行为 | 默认值、错误类型、取消与关闭语义、上限——ABI 看不到这些，需由契约测试与变更记录覆盖 |
| 工具链 | 发布所用的 Kotlin 版本、OpenSSL 版本；实测过的"生产者 / 使用者 Kotlin 版本组合"矩阵 |

- **版本号**：1.0 之前，破坏性变更升次版本（0.x → 0.(x+1)），其余升修订版本；1.0 起遵循语义化版本。
- **弃用**：先标记 `@Deprecated` 并给出替代，至少保留一个次版本周期后移除（1.0 之前的占位类除外，例如 msgtrans 移除的 `QuicClientTransport` /
  `WebSocketClientTransport` 存根，它们从未可用）。
- **Kotlin 版本**：klib 的跨版本兼容取决于库的种类——纯 Kotlin 代码与含 cinterop 的产物不同，编译器插件另论。以实测的兼容矩阵为准，
  不做一刀切的声明；当前所有库以 Kotlin 2.4.20 构建，构建脚本拒绝更低版本。
- **版本组合**：各库版本号独立；维护一份**验证过的版本组合**（哪些版本一起测过），不同版本号本身不是缺陷。是否提供 BOM 以及 BOM 对
  KMP / Native 使用者的实际效果，需实测后再定。

## 9. 性能

- **固定场景与条件**：硬件、核数与 cpuset、驱动、连接数、负载工具与版本、请求内容；与参考实现在同一条件下对照。
- **重复与噪声**：多轮、交替 A/B，报告分布而不是单次最好值；单核成本用指令数（cachegrind）衡量，吞吐数对用于确认，不单独作结论。
- **先复现再定位**：观察到的退化（例如 HttpArena 多核结果）先在可控环境复现，再以分析工具（perf、调度与锁统计、GC 日志、分配归因）
  定位根因；在定位之前不把假设写成结论。
- **门槛**：每个库定义自己的基准场景与预算（吞吐、p99、每请求指令数、每请求分配）。超出预算阻断发版；安全修复可按 §11 例外先发布。
- 同一宿主上的负载会互相干扰；共享机器上的结果需附负载记录。

## 10. 安全

- **报告渠道与响应**：每个仓库的 `SECURITY.md` 指向同一份策略（[security](./security.md)）。响应时限由维护者确定后写入。
- **依赖跟进**：OpenSSL 发布安全版本后，openssl 产物与依赖它的库（tls、quic）按策略中的时限跟进。
- **模糊测试与检测**：§7.5；cinterop 的 C 代码（各库的 shim、vendored zstd）定期以 AddressSanitizer / UndefinedBehaviorSanitizer 运行。
- **安全默认值**：比参考实现更严格的默认（例如 http 拒绝同时带 Transfer-Encoding 与 Content-Length 的请求）记录在支持声明中。

## 11. 例外

阻断项（未解释失败、性能超预算、兼容性破坏）可以例外放行，条件：
- 写明例外的内容、原因、风险、到期条件（何时必须解决）；
- 由维护者批准；记录在发版说明与对应库的支持声明中；
- 安全修复优先：可在其他门槛未满足时发布，但事后补齐并记录。

## 12. 可追溯发布

每个发布产物必须能追溯到：
- 源码提交与标签；
- 依赖的确切版本（POM / Gradle module 中的依赖坐标）；
- 工具链：Kotlin 版本、OpenSSL 版本（含 cinterop 的产物）；
- 发版前的 CI 运行（测试、外部套件、互通）链接；
- 签名（当前：Maven Central 要求的 GPG 签名）。

目标（尚未达到）：由 CI 而非个人机器构建并发布；发布附 SBOM；构建可重复。当前的发布记录见 [releases](./releases.md)。
